# Hub panel

## Summary

An authenticated control panel served by the hub service. It uses the
Clara Lab workbench layout: a title bar, an activity rail with tabbed views, and
a status bar. It shows the hub's live state, transports, browser clients,
harness adapters, the active harness probe, push health, configuration sources,
database health, storage files, and a live traffic meter without exposing
secrets. The active harness is the panel's default backend: any number of
harnesses can be paired and serve their own workspaces, while a request that
names neither a session nor a workspace falls back to the active one. Sensitive values, including the
harness URL and relay room, start masked behind a header peek control so the
panel can be screenshared safely. It is also the setup
surface for browser pairing and harness adapters: the superadmin signs in,
chooses a password, then creates a one-time browser link, code, or QR, or adds an
adapter and runs its install command on the harness machine. The same surface
edits the Web URL used by pairing links, the VAPID contact used by Web Push, and
the relay target, switches external connections on and off without stopping the
process, starts and stops the local orchestration service, turns traffic
monitoring on or off, and gates or paces client settings sync. Relay rooms are
always generated by the hub and can only be replaced with another random value.
A build compiled with `ENABLE_CLOUDFLARE_DEPLOYMENT=true` also deploys the relay
Worker and Durable Object to the operator's Cloudflare account from the Relay
card.

## User flow

1. Start the hub after `pnpm build` with `pnpm clara server start --local`, or
   `pnpm clara server start` for the container, then run
   `pnpm clara server panel`. The open command only opens a panel that is
   already being served; the start command prints the panel URL
   (`http://127.0.0.1:8790/` by default).
2. The command opens the panel. First run shows setup: read the one-time token
   from `admin-setup.txt` in the config directory, or run
   `pnpm clara server setup-token` (it targets the running deployment
   automatically), then choose the superadmin password. Later visits show the
   sign-in form. After a host reset, the sign-in form shows a reset link while
   the token is valid.
3. After signing in, open **Harness**, use **Add harness**, choose the adapter
   type and location, then copy the pairing code or install command. Run the
   command on the harness machine. A new adapter appears under
   **Paired harnesses** as **Paired · Offline**; when its credential session
   connects it also appears under **Connected adapters**, becomes **Online**,
   and the first adapter becomes **Active**, the default for screens that do not
   name a session or workspace. The pending pairing card returns
   to the add form as soon as the adapter registers. Use **Test** to probe an
   adapter. In a container, the adapter connects to `ws://server:8788/ws` on
   the `clara` network; `127.0.0.1` means the hub host.
4. The panel opens on **Overview** with the Hub and Orchestration cards, a
   health strip for Harness, Local, Relay, Push, and Orchestration, the five most
   recent events, and a storage summary. A **Needs attention** banner names every
   degraded surface; health tiles jump to their tab. Status chips sit beside each
   card title, including a storage health summary that turns amber for warnings
   and red for errors. Sensitive values start masked: device ids and fingerprints,
   config and storage paths, local WebSocket endpoint, harness URL, relay URL and
   room, connection session ids, and WebSocket URLs in activity or errors.
5. Move between views from the activity rail: **Home** (Overview), **Harness**,
   **Network** (Connections), **Clients**, **Traffic**, and **Activity**, with
   **Settings** pinned at the bottom. The rail shows live client and event counts
   and amber or red dots for trouble. Views are hash links (`#traffic`,
   `#clients`), keep their scroll position while you switch, and survive a
   reload. Cards open by default inside their view; click a header to collapse
   it. Cards with a feature switch can only be expanded while that feature is
   enabled.
6. The title bar shows the connection badge, the last update, the peek control,
   **Refresh**, and **Sign out**. The status bar along the bottom summarizes the
   hub, harness, local, relay, push, orchestration, and client state; each item
   opens the matching view. Its far end shows the panel version with the build
   commit and the panel API version, such as `v0.1.0.c8becb85 · API v11`.
7. **Harness** mirrors the Clients view. The page header carries the active
   harness health badge. **Add harness** sits first and owns the harness type,
   adapter location, and pairing code; the form lays the two choices out in a
   grid, and the latched pairing card returns to the form after the adapter
   registers. **Connected adapters** follows with live adapter sessions:
   transport, session id, harness label and kind, short harness id, credential
   fingerprint, timestamps, and the same traffic counters as Clients.
   **Paired harnesses** sits at the bottom with the label, kind, fingerprint,
   transport, version, status, last seen, and last test for every enrolled
   adapter. Each paired row carries **Activate**, **Test**, **Delete**, and
   **Forget**. A paired adapter shows **Active** when selected and one status
   badge: **Online** for a live session, **Paired · Offline** when the
   credential exists but no session is connected, **Not paired** before
   enrollment, or **Off** while harness access is disabled. **Active** only
   chooses the default backend; projects, sessions, and workspaces on other
   paired harnesses keep working through their own scope.
8. In **Connections**, toggle local transport, relay, or push from the switch at
   the top right of its card. The choice is saved immediately. An enabled switch
   is green while external connections are on and red while they are off; a disabled switch
   keeps its neutral track in both cases. Turning a feature off hides its
   details; turning it on makes the header expandable. The Relay card edits the
   relay URL, hub token, and client token, shows the generated room, and can
   regenerate that room. Tokens are encrypted before they are saved and are
   never shown again. A relay URL saved without tokens does not block the hub:
   the card marks both tokens as missing and the hub runs local-only until they
   are saved. Environment variables win over panel values field by
   field; fields they supply are read-only. When the build includes the optional
   Cloudflare deployment, the Relay card also carries **Deploy relay to
   Cloudflare**: paste a Workers-scoped API token, choose the account, and Clara
   uploads the Worker, creates the Durable Object namespace, sets both relay
   tokens, and connects the relay. Existing devices must pair again.
9. In **Settings**, choose **Light**, **Dark**, or **System** under **Appearance**.
   **System** follows the operating system setting. The choice is stored in this
   browser and applies to the sign-in screen too.
10. In **Settings**, edit **Web URL** or **VAPID contact** and choose **Save**;
    **Use default** clears the file value. The source tag shows environment,
    `server.json`/`vapid.json`, or default, and an environment value locks the
    field.
11. In **Settings**, use the **Shell commands** switch to enable or block all
    command requests. Enabling makes the header expandable; open it to edit
    **Filter commands**, optionally turn on **Allow Git history**, then choose
    **Apply** at the bottom right. **Discard** sits to its left. The switch stays
    amber until Apply succeeds, then turns green. Turning it off blocks every
    command immediately. Empty filters mean every command is allowed, and the
    card warns about it.
12. In **Settings**, turn client sync on or off for every paired client, and
    choose the interval at which those clients check for changes. Turning it off
    hides the web Sync tab and rejects sync requests; the stored namespace and
    each device's category choices remain. The interval defaults to 30 seconds.
13. To take every external connection offline, choose **Go offline** at the top
    right of the Hub card on Overview and confirm. The page keeps polling; the
    banner explains that the panel is still available.
14. Choose **Go online** to restore the saved choices. Feature switches are
    disabled until connections are back online and show red while they are
    stopped, so the offline state is readable from the switch colors alone.
15. In **Clients**, use **Pair a browser** to create a one-time link, code, or
    QR for a browser or installed app. Choose **Relay** or **Local** before
    creating the code; the helper text explains where that code works. The
    ready card shows only the QR until **Show codes** is opened, where the link,
    code, fingerprint, transport, and expiry live; it can cancel the code before
    it is used. Review the browser client table and paired devices below. Harness
    adapter sessions are not listed here; they live under **Harness**. A
    one-time pairing session appears with a **Pairing** badge and no device until
    enrollment finishes; it is excluded from the active count and the local E2EE
    session count. Each paired session row shows the device's display name, short
    device id, and fingerprint so devices that share a label stay distinguishable.
    An active device's **Edit** action sets an alias of up to 64 characters; the
    enrolled label stays visible as secondary text, and clearing the alias restores
    the enrolled name. Connected clients resolve the same alias from the paired
    device list, so a rename applies on the next snapshot without reconnecting.
    Status badges call out degraded harness, relay, push, permissions, or
    missing files.
16. In **Traffic**, read the last minute's in and out rates, the request and
    error rates, the two sparklines for the last hour, and the totals since the
    window started. The card shows the local-versus-relay split, a peak minute,
    and the error breakdown. An amber **Spike** badge means the last complete
    minute was at least three times the previous half hour and above a floor; it
    is a hint, not a verdict.
17. Use the switch at the top left of **Traffic** to stop recording. The card
    collapses to its header, the counters are discarded, and the client table
    drops its traffic columns. Turning it back on starts a fresh window with a
    one-minute warm-up. The switch stays usable while external connections are off.
18. In **Activity**, read the in-memory events and the storage list. The storage
    header summarizes the most severe entry and its count, and the overview links
    here for the full list.
19. Use **Orchestration** on Overview to start or stop the local orchestration
    service. Turning it on starts a detached local instance when nothing is
    answering and waits for `/health`; turning it off stops only the local
    instance started from this data directory. A Docker or external instance is
    detected and labelled, and the switch is disabled because the panel does not
    own it. When the service is reachable, Clara groups worker sessions in
    **Workers** and keeps their session alerts quiet.
20. Leave the page open. It refreshes every five seconds while visible and
    pauses when the tab is hidden. Use **Refresh** for an immediate check.

## Core business rules

1. **Authenticated, and loopback by default.** The panel listens on
   `127.0.0.1:8790` by default. A container binds `0.0.0.0` inside its own
   network and publishes only on host loopback. Every API request except
   `/health`, the session endpoints, setup, and static assets requires a
   superadmin session. `CLARA_PANEL_BIND_HOST` and `CLARA_PANEL_ALLOW_REMOTE` are
   explicit exposure controls. The `Host`/`Origin` guard still expects a
   loopback origin, so remote access uses an SSH tunnel rather than direct LAN
   access. It is never served through the relay or Pages.
2. **First run is a one-time token, not a default password.** With no admin,
   the server writes `admin-setup.txt` (mode `0600`) in the config directory.
   The setup form exchanges that token for a username and a scrypt-hashed
   password. A lost password is reset only by the host-side
   `clara-server admin reset`, which writes a fresh token and revokes sessions.
   There is no network password-reset endpoint.
3. **Reads and writes require a session.** `GET` and `HEAD` serve the snapshot
   and assets after login. `POST` is accepted at the feature, master-stop,
   monitoring, sync, orchestration, config, harness, browser-pairing, password,
   and device-purge routes; `PATCH` changes a device alias; `DELETE` revokes a
   device, cancels a browser pairing code, and removes a harness or the session.
   Unknown mutating methods return `405`.
4. **Secrets stay out of the snapshot.** The snapshot is built from an explicit
   allowlist. Device keys, enrollment codes, adapter credentials, relay tokens,
   push endpoints, sync values, and file contents are never returned there. A
   one-time browser or adapter pairing code is returned only by the authenticated
   request that creates it. Device keys and unused enrollment tokens are
   encrypted at rest in SQLite with a key outside the database. Relay tokens are
   encrypted with the same key in `relay-credentials.json`; the URL and generated
   room stay in `server.json`. Device fingerprints, secret-configured flags, room
   id, and effective config values are included and start masked in the panel.
5. **Mutations are browser-hard to forge.** Besides authentication, the
   `Host`, `Origin`, and `Sec-Fetch-Site` checks, writes require
   `x-clara-panel: 1`; a write with a JSON body also requires
   `content-type: application/json`. Mutations reject unknown fields and cap the
   body at 8 KB. The custom header forces a CORS preflight for cross-origin
   pages, which the server rejects. No CORS headers are sent. Login and setup
   are rate-limited per source and username.
6. **Settings are durable.** Feature choices, the stopped flag, the monitoring
   choice, the orchestration switch, the client-sync gate and interval, the
   panel users, and harness connections live in the
   hub's SQLite database and are loaded before any transport starts. The panel
   can fail without stopping the hub service; a busy panel port only loses the panel.
   The Web URL and relay URL/room live in `server.json`, the VAPID contact in
   `vapid.json`, and relay tokens in the encrypted `relay-credentials.json`; the
   panel writes all of them, the environment overrides any field, and the VAPID
   contact and relay target are applied live. The appearance choice is
   browser-local: it never reaches the hub service or its database.
7. **Traffic monitoring is advisory and in memory.** The meter counts frame
   sizes, decrypted request actions, and the failures the hub already detects;
   it never reads or stores payloads. Counters live in a sixty-minute ring of
   one-minute buckets and reset on restart or when monitoring is switched off.
   Nothing is throttled, blocked, or persisted, and the per-client counters are
   hidden while monitoring is off.
8. **Peek is presentation-only.** The eye button masks device ids and
   fingerprints, config and storage paths, local WebSocket endpoint, harness
   URL, relay URL and room, connection session ids, and WebSocket URLs in
   activity messages and error notices. The Home health tiles and status bar
   tooltips use the same scrubber. It does not redact the JSON snapshot, change
   any control, or reach the hub service: its allowlist remains the security
   boundary. The choice lives in `sessionStorage` for the tab, so a reload
   keeps it and a new tab starts masked.

## Edge cases

- **No harness is configured** — **Add harness** starts open, and the header
  says **Not configured**. Harness-backed `/v1` requests return
  `503 harness_unconfigured` until an adapter is paired and activated. The web
  can still connect and shows a harness banner.
- **The adapter is paired but offline** — **Paired harnesses** says
  **Paired · Offline**, the probe is not run, and harness-backed `/v1` returns
  `harness_offline`. Start the adapter service; it reconnects automatically.
- **Harness access is disabled** — the page header and paired status say
  **Off**, the probe is not run, and proxied requests fail with a disabled
  error. Local and relay clients stay connected. The legacy harness feature gate
  has no switch in the Harness header because multiple harnesses are supported.
- **The adapter credential cannot be opened** — the connection stays listed but
  cannot authenticate. Re-pair the adapter; the rest of the hub keeps running.
- **The setup token is missing** — the panel explains how to run
  `pnpm clara server setup-token` or `clara-server admin reset`. It does not
  fall back to a default password.
- **The setup token is wrong or expired** — setup returns a generic invalid-token
  error and keeps the form available. Run the host reset command to issue a new
  token.
- **The superadmin password is lost** — run `pnpm clara server admin reset`. It
  targets the running deployment automatically and prints which one it chose,
  writes a new one-time token, and revokes every panel session. While that token
  is valid, the sign-in screen shows **Lost your password? Use a reset token**;
  the form takes the token and a new password and keeps the existing username.
  The link disappears when the token is used or expires. There is no HTTP reset
  route.
- **A local install and the Docker stack both have state** — the command refuses
  to guess and exits after printing the reason. Pass `--docker` for the
  `clara-server` container or `--local` for the local install.
- **The session expires** — the next poll returns `401`, the dashboard is
  replaced by the sign-in screen, and no stale data is shown.
- **The panel is reached through the Docker bridge** — `CLARA_PANEL_ALLOW_REMOTE`
  skips only the socket-address check; authentication, `Host`, `Origin`, and
  fetch-metadata checks still apply. Keep the published port on host loopback.
- **Local transport is off** — the card says off and the listener closes its
  clients with a clear reason. Turning it on starts a fresh listener.
- **Relay is not configured** — the relay card explains local-only mode and
  opens the relay editor. Saving a URL and both tokens generates a room and
  connects without restarting the hub.
- **The relay room is regenerated** — every pairing code and stored client
  token tied to the old room becomes invalid; the panel asks for confirmation
  first.
- **Relay settings come from the environment** — each field supplied by
  `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`, `CLARA_AGENT_TOKEN`, or
  `CLARA_CLIENT_TOKEN` is read-only and wins over the panel value. Remove the
  variable and restart the hub service to edit that field here.
- **Relay reconnects** — the card shows the current state, last change, attempt
  count, and a redacted error.
- **Push is off or unavailable** — the card shows the saved choice, the
  effective state, the startup error, and the subscription count. Existing
  subscriptions are kept.
- **Client sync is off** — the web Sync tab disappears, sync actions return
  `disabled`, and the stored namespace and per-device category choices are kept
  for the next enable.
- **Sync interval changes** — connected clients receive the new cadence in a
  hub status update and reschedule their next check without reconnecting.
- **Connections are off** — a banner says external connections are off, every
  transport card shows a stopped state, feature switches are disabled, and
  **Pair a browser** cannot create a code. An enabled feature switch turns red
  and a disabled one keeps its neutral track. The Traffic and Client sync
  switches keep their usual colors.
- **Orchestration changes** — the hub probes `/health` before and after
  the action, then broadcasts the new `orchestration` flag so connected clients
  add or remove the Workers treatment without a reload. A failed local start
  keeps the error on the card. A Docker or external instance cannot be stopped
  from the panel.
- **A feature fails to start** — the saved choice remains, the card shows the
  error, and the rest of the hub keeps running.
- **No browser clients** — the client table shows an empty state and **Pair a
  browser** sits above it. A connected harness adapter still appears under
  **Harness → Connected adapters**.
- **A harness adapter is connected** — it has its own row under
  **Connected adapters** with its harness label, kind, short harness id, and
  credential fingerprint. It never appears in the Clients table or its counts.
- **A pairing session is listed** — the row carries a **Pairing** badge instead
  of a device. It is the one-time enrollment connection, not a failed client,
  and the hub retires it as soon as the device-enrolled response is sent.
- **A browser pairing code is cancelled or expires** — it cannot enroll a
  device. Create a new code; the cancelled token is removed immediately and an
  expired token is pruned on the next creation or pair command.
- **The panel is screenshared** — sensitive values load masked and the eye
  button reveals them for the tab. Masked values lose their full-value tooltips
  and copy buttons, and the same scrubber covers activity messages, error
  notices, Home health tiles, and status bar tooltips.
- **Monitoring is off** — the Traffic card collapses to its header and switch,
  the client table drops its traffic columns, and no counter moves. Turning it
  on starts a new window.
- **Monitoring is switched off mid-stream** — the counters stop where they are
  and the window is discarded. The stream itself keeps flowing.
- **The first minute after enabling or restarting** — the card says collecting
  and shows no rate or spike until one full minute has been measured.
- **A spike is detected** — the badge and notice name the signal that crossed
  the threshold. A large but legitimate stream raises it too.
- **A storage entry is unhealthy** — the storage header shows an error badge
  when any entry failed, otherwise a warning badge for read-only files, broad
  permissions, or missing required files. The tooltip counts each state.
- **Config permissions are broad** — storage warns when the database,
  `server.json`, `secrets.key`, `admin-setup.txt`, subscriptions, or VAPID keys
  are readable by other users.
- **The panel was not built** — the page returns a short instruction to run
  `pnpm build`; the JSON API still works.
- **Panel port is busy** — the hub service logs `panel unavailable` and continues.

## Out of scope

- Non-superadmin panel users and roles; the schema reserves a role column
- Remote access to the panel through the relay
- Editing the relay room as free text; rooms are generated by the hub and can
  only be regenerated. The panel does not edit other `server.json` fields beyond
  the Web URL, relay URL, and generated room
- Cloudflare custom domains, Worker deletion, or account selection beyond the
  one account used for a relay deployment
- A second active harness or per-client selection in the panel header; the panel
  stores one active backend as the default for requests that name no session or
  workspace, while paired harnesses keep serving the workspaces and sessions
  scoped to them
- Per-device relay tokens; the relay client token remains shared
- A sandbox for command execution, or an allowlist of every proxied API route
- Per-command arguments, wildcards, or regular expressions in the allowlist
- Rate limiting, blocking, or alerts driven by the traffic meter
- Historical metrics beyond the sixty-minute window, persisted logs, or an audit
  trail
- Reading, editing, or deleting individual synced values or namespaces from the
  panel; it controls only the global gate and cadence

## Known gaps

- Authentication is not host isolation. A process with the panel cookie, the
  database, or `secrets.key` can still act as the hub; keep the config and
  data directories private.
- Sessions are in memory, so restarting the hub service signs everyone out.
- The superadmin password is hashed; adapter credentials are reversible and
  must be encrypted at rest with a backed-up key.
- Device identity is logical, not hardware-bound. The panel shows one row per
  stored device and one row per live connection; multiple tabs share a device.
- Traffic is measured at the hub, so connections the relay rejects before they
  reach it, and Cloudflare-level bandwidth, are visible only in Cloudflare
  analytics.
- The traffic window and the activity list are in memory and reset when the
  hub service restarts.
- A session that spans a monitoring toggle shows only the traffic recorded while
  monitoring was on.
- The active harness probe is cached for five seconds, so the header can briefly
  lag a restart.
- The peek control hides values in the rendered panel only. The JSON snapshot
  still contains them, so browser devtools and the network panel can show them.

- Panel listener: `127.0.0.1:8790` by default; `CLARA_PANEL_BIND_HOST=0.0.0.0`
  inside the container with host-loopback publishing
- Page: `GET /`
- Health: `GET /health` (unauthenticated, no secrets)
- Session: `GET|POST|DELETE /panel/api/v1/session`
- Setup: `POST /panel/api/v1/setup` with `{ "token": "...", "username": "...", "password": "..." }`
- Read API: `GET /panel/api/v1/status` (API version `11`, authenticated)
- Mutations:
  - `POST /panel/api/v1/features` with `{ "feature": "...", "enabled": true }`
  - `POST /panel/api/v1/agent` with `{ "stopped": true }` (external connections off)
  - `POST /panel/api/v1/orchestration` with `{ "enabled": true }`
  - `POST /panel/api/v1/config` with `{ "pairingBaseUrl": "https://..." }` or
    `{ "vapidSubject": "mailto:..." }`; send `null` to restore the default
  - `POST /panel/api/v1/relay` with `{ "url": "wss://...", "agentToken": "...", "clientToken": "..." }`;
    omitted tokens keep their saved values, and `room` is rejected
  - `POST /panel/api/v1/relay/room` generates a new random room
  - `DELETE /panel/api/v1/relay` clears the panel relay target and sealed tokens
  - `POST /panel/api/v1/monitoring` with `{ "enabled": false }`
  - `POST /panel/api/v1/sync` with `{ "enabled": true, "intervalMs": 30000 }`
  - `POST /panel/api/v1/harnesses/pairings` creates an adapter pairing code
  - `DELETE /panel/api/v1/harnesses/pairings/:id` cancels one
  - `POST /panel/api/v1/harnesses/:id/test|activate|forget`
  - `DELETE /panel/api/v1/harnesses/:id`
  - `POST /panel/api/v1/devices/pairings` with `{ "localOnly": true }` creates a
    browser pairing link, code, and fingerprint
  - `DELETE /panel/api/v1/devices/pairings/:id` cancels an unused browser code
  - `DELETE /panel/api/v1/devices/:id` revokes the device
  - `PATCH /panel/api/v1/devices/:id` with `{ "alias": "Desk MacBook" }` renames
    it; send `{ "alias": null }` to restore the enrolled label
  - `POST /panel/api/v1/devices/:id/purge` deletes a revoked device record
  - `POST /panel/api/v1/account/password`
- Required mutation headers: `x-clara-panel: 1`; JSON-body mutations also
  require `content-type: application/json`
- Assets: `GET /assets/<hashed file>` and `GET /favicon.svg`
- Environment:
  - `CLARA_PANEL_PORT` changes the port (default `8790`)
  - `CLARA_PANEL_BIND_HOST` changes the listener (default `127.0.0.1`)
  - `CLARA_PANEL_ALLOW_REMOTE=1` permits a container bridge source; auth remains required
  - `CLARA_PANEL_SECURE_COOKIE=1` for a loopback-preserving HTTPS proxy
  - `CLARA_PANEL_DISABLED=1` disables the panel
  - `CLARA_PAIRING_BASE_URL` overrides the panel Web URL
  - `CLARA_VAPID_SUBJECT` overrides the panel VAPID contact
  - `CLARA_WEB_PORT` sets the default Web URL port (default `8080`)
  - `CLARA_DB_PATH` moves the database (default `<data dir>/clara.db`)
  - `CLARA_SECRET_KEY` or `CLARA_SECRET_KEY_FILE` encrypts adapter credentials; otherwise
    `secrets.key` is generated in the config directory
  - `CLARA_ADMIN_SETUP_TOKEN` or `CLARA_ADMIN_SETUP_TOKEN_FILE` supplies the first-run token
- CLI: `clara-server serve --no-panel`, `clara-server admin reset|setup-token`
- Built assets: `apps/hub/server/dist/panel`, copied from `apps/hub/panel/dist`
- Open the built panel: `pnpm clara server panel` opens
  `http://127.0.0.1:${CLARA_PANEL_PORT:-8790}/` in a browser when the hub service is
  already serving it; start the hub with `pnpm clara server start --local`
  (or `--docker`) first. The panel is a surface of the hub, not a
  separate service
- Docker (default): `pnpm clara server start|stop|restart|status|setup-token|pair|admin|logs`;
  `setup-token`, `admin`, and `pair` target the running deployment
  automatically, and `--docker`/`--local` force the container or the host
  install. Pass `--local` to `start`, `stop`, `restart`, or `logs` to use
  the detached local hub instead. `pair --no-relay` emits a local-only code.
  The rebuild snapshot records the hub as `container` or `local` and
  recreates a container with stop/start instead of signalling a PID. See
  [maintenance.md](maintenance.md).
- Dev UI: `pnpm dev:panel` (Vite on `5174`, proxying `/panel/api` to `8790`; the
  proxy rewrites `Host` and `Origin`, and the browser carries the session cookie)
- Snapshot sections: hub, auth, config, harness, harnesses, devices, local transport,
  relay, clients (browser and adapter sessions), push, controls (feature switches,
  monitoring, sync, orchestration), storage, events, traffic
