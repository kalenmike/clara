# Hub panel

## Summary

An authenticated control panel served by the hub service. It uses the
Clara Lab workbench layout: a title bar, an activity rail with tabbed views, and
a status bar. It shows the hub's live state, transports, browser clients,
harness adapters, aggregate harness health, agent sessions across every paired
harness, push health, configuration sources, database health, storage files,
and a live traffic meter without exposing secrets. Every paired harness is a
peer: there is no active or default backend, and a request that names neither a
session nor a workspace must name its harness. Sensitive values, including the
harness URL and relay room, start masked behind a header peek control so the
panel can be screenshared safely. It is also the setup
surface for the owner account, browser pairing, and harness adapters: on first
run it serves only a local setup screen until the owner account exists, then the
hub starts its transports and the superadmin can create a one-time browser link,
code, or QR, or add an adapter. Adapter installs can be run over SSH or Docker
from the hub host, or copied as a registry command for a manual install. The same surface
edits the Web URL used by pairing links, the VAPID contact used by Web Push, and
the relay target, switches external connections on and off without stopping the
process, starts and stops the local orchestration service, turns traffic
monitoring on or off, and gates or paces client settings sync. Relay rooms are
always generated by the hub and can only be replaced with another random value.
A build compiled with `ENABLE_CLOUDFLARE_DEPLOYMENT=true` also deploys the relay
Worker and Durable Object to the operator's Cloudflare account from the Relay
card.

## User flow

1. Start the hub after `pnpm build` with `pnpm clara start hub --local`, or
   `pnpm clara start hub` for the container, then run
   `pnpm clara status hub --open`. The open command only opens a panel that is
   already being served; the start command prints the panel URL
   (`http://127.0.0.1:8790/` by default).
2. On first run the panel is the only surface. It shows **Create the hub owner
   account** with a username, password, and confirmation. No local WebSocket,
   relay, harness probe, push monitor, orchestration, or pairing starts until
   that account exists. The setup route is local-only; remote requests are
   rejected by the panel's Host/Origin/fetch-metadata guards. Choose the owner
   credentials and submit; the hub starts its transports in the same process and
   the dashboard replaces the setup screen. Later visits show the sign-in form.
   A host reset adds a reset link while its token is valid. For a headless
   install, run `node apps/hub/server/dist/index.js setup --password-stdin` while the hub is in
   setup mode, or set `CLARA_ADMIN_USERNAME` and `CLARA_ADMIN_PASSWORD` (or
   `CLARA_ADMIN_PASSWORD_FILE`) before starting it. The environment path creates
   the owner before any transport starts and skips the setup screen. A
   host-supplied `CLARA_ADMIN_SETUP_TOKEN` switches the setup screen to token
   mode for an explicitly remote or automated install.
   After the owner account is created, a dismissible **Setup** modal opens over
   the dashboard. It asks for the connection path first: **Local only**, or
   **Remote via relay** with the relay editor and Web URL embedded in the same
   step. The modal then pairs a harness and a client and ends with **How Clara
   works**. Required steps are the connection path, a paired harness, and a
   paired client. The relay step cannot be skipped by leaving it half
   configured: either the relay is online with an HTTPS Web URL, or the user
   chooses Local only. The modal can be skipped and resumed from **Settings →
   Setup**. After it is complete it does not reopen automatically. The same flow
   is available from **Settings → Setup → Reconfigure connections**, which
   starts at the connection path with the current values, and the guide is
   available from **Replay setup guide**. Reconfiguring a relay or its room can
   require adapters and devices to pair again.
3. After signing in, open **Harness** and use **Pair Harness**. Choose the
   adapter type, then answer **Remote** or **Local**. Remote installs over SSH
   from `~/.ssh/config` or a typed user/host/port and uses the relay. Local asks
   whether the adapter runs **on this machine** or **in a Docker container**:
   a container target on a Docker-hosted hub uses the Docker network
   (`ws://server:8788/ws`), while on a host-process hub it uses the relay.
   Both branches run the registry install script on the target and stream the
   log back, and both offer **Copy code** and **Copy command** for a manual
   install. Install actions are off until they are enabled in **Settings →
   Adapter downloads**, and a containerized hub cannot run them at all; in that
   case the pairing still produces the container target's code and command and
   the panel explains that the hub runs in Docker. The pairing card shows
   **Waiting for the adapter to connect…**, switches to **Connected**, and the
   footer becomes **Done** when the adapter registers. A new adapter appears
   under **Paired harnesses** as **Paired · Offline**; when its credential
   session connects it also appears under **Connected adapters** and becomes
   **Online**. Use **Test** to probe an adapter. In
   a container, the adapter connects to `ws://server:8788/ws` on the `clara`
   network; `127.0.0.1` means the hub host.
4. The panel opens on **Overview** with a six-tile health strip — Hub, Local,
   Relay, Harness, Push, and Orchestration — then Active clients and Active
   adapters previews, the five most recent events, and a storage summary. The
   Hub tile leads with its connection state and platform, process, and version;
   the **Go offline** control sits at the far right of the Overview header. A
   **Needs attention** banner names every degraded surface; health tiles jump to
   their tab, and the Hub tile opens Settings. The Active clients and Active
   adapters cards show up to five live rows with transport, paired device or
   harness, connected, and last seen, and link to the full Clients and Harness
   tables. Status chips sit beside each card title, including a storage health
   summary that turns amber for warnings and red for errors. Sensitive values
   start masked: device ids and fingerprints, config and storage paths, local
   WebSocket endpoint, harness URL, relay URL and room, connection session ids,
   and WebSocket URLs in activity or errors.
5. Move between views from the activity rail: **Home** (Overview), **Harness**,
   **Sessions**, **Network** (Connections), **Clients**, **Traffic**, and
   **Activity**, with **Settings** pinned at the bottom. The rail shows live client and event counts
   and amber or red dots for trouble. Views are hash links (`#traffic`,
   `#clients`), keep their scroll position while you switch, and survive a
   reload. Cards open by default inside their view; click a header to collapse
   it. Cards with a feature switch can only be expanded while that feature is
   enabled.
6. The title bar shows the connection badge, the last update, the peek control,
   **Refresh**, and **Sign out**. The status bar along the bottom summarizes the
   hub, harness, local, relay, push, orchestration, and client state; each item
   opens the matching view. Its far end shows the panel version with the build
   commit and the panel API version, such as `v0.1.0.c8becb85 · API v12`.
7. **Harness** mirrors the Clients view. The page header carries a **Pair
   Harness** button that opens the two-step pairing modal. The modal owns the
   harness type, the Remote or Local answer, the install target, and the pairing
   code, and it returns to the first step after the adapter registers.
   **Connected adapters** follows with live adapter sessions:
   transport, session id, harness label and kind, short harness id, credential
   fingerprint, timestamps, and the same traffic counters as Clients.
   **Host resources** follows with a sample from every online adapter that
   reports one: CPU and memory usage, disk space for the adapter data and config
   directories, a **container** badge when cgroup limits apply, and the sample
   age. A sample describes the adapter machine or container, not the harness's
   workspace volumes. Adapters that predate the endpoint show an empty state.
   **Paired harnesses** sits at the bottom with the label, kind, fingerprint,
   transport, version, status, last seen, and last test for every enrolled
   adapter. Each paired row carries **Test**, **Delete**, and **Forget**, and
   shows one status badge: **Online** for a live session, **Paired · Offline**
   when the credential exists but no session is connected, **Not paired**
   before enrollment, or **Off** while harness access is disabled. The Harness
   tile reports how many paired harnesses are online; it does not pick one.
8. Open **Sessions** to monitor agent work across every paired harness. Each
   harness has a status card with its session and running counts; offline,
   disabled, and partial harnesses stay visible without hiding the others. The
   table lists running, awaiting-input, and idle sessions with title, harness,
   agent, directory, model, and last update. Use the search box, harness picker,
   **Running only**, and **Show archived** to narrow the list. Open a row for
   the session ID, directory, project, parent session, model, and timestamps.
   Session IDs and directories follow the header peek control. The view is
   read-only and refreshes while it is visible.
9. In **Connections**, toggle local transport, relay, or push from the switch at
   the top right of its card. The choice is saved immediately. An enabled switch
   is green while external connections are on and red while they are off; a disabled switch
   keeps its neutral track in both cases. Turning a feature off hides its
   details; turning it on makes the header expandable. The Relay card edits the
   relay URL and hub token, shows the generated room, and can regenerate that
   room. The token is encrypted before it is saved and is never shown again. A
   relay URL saved without the hub token does not block the hub: the card marks
   the token as missing and the hub runs local-only until it is saved.
   Environment variables win over panel values field by field; fields they
   supply are read-only. When the build includes the optional Cloudflare
   deployment, the Relay card also carries **Deploy relay to Cloudflare**: paste
   a Workers-scoped API token, choose the account, and optionally attach a custom
   hostname in one of its zones. Clara uploads the Worker, creates the Durable
   Object namespace, sets the hub token, and connects the relay. A custom
   hostname waits for its certificate before Clara disables the workers.dev
   host. Existing devices must pair again to receive a v4 grant.
10. In **Settings**, review the full **Hub** details (uptime, process, platform,
    memory, config path, and paired devices) and the **Orchestration** master
    switch, then choose **Light**, **Dark**, or **System** under **Appearance**.
    **System** follows the operating system setting. The choice is stored in this
    browser and applies to the sign-in screen too.
11. In **Settings**, edit **Web URL** or **VAPID contact** and choose **Save**;
    **Use default** clears the file value. The source tag shows environment,
    `server.json`/`vapid.json`, or default, and an environment value locks the
    field.
12. In **Settings**, use the **Shell commands** switch to enable or block all
    command requests. Enabling makes the header expandable; open it to edit
    **Filter commands**, optionally turn on **Allow Git history**, then choose
    **Apply** at the bottom right. **Discard** sits to its left. The switch stays
    amber until Apply succeeds, then turns green. Turning it off blocks every
    command immediately. Empty filters mean every command is allowed, and the
    card warns about it.
13. In **Settings**, turn client sync on or off for every paired client, and
    choose the interval at which those clients check for changes. Turning it off
    hides the web Sync tab and rejects sync requests; the stored namespace and
    each device's category choices remain. The interval defaults to 30 seconds.
14. To take every external connection offline, choose **Go offline** at the far
    right of the Overview header and confirm. The Hub tile reads **Connections
    inactive**; the page keeps polling and the banner explains that the panel is
    still available.
15. Choose **Go online** to restore the saved choices. Feature switches are
    disabled until connections are back online and show red while they are
    stopped, so the offline state is readable from the switch colors alone.
16. In **Clients**, choose **Pair Client** in the page header to open the
    pairing dialog. Choose **Relay** or **Local** before creating the code; the
    helper text explains where that code works. **Create pairing link** switches
    the dialog to the pairing view: a locally rendered QR, an **Open Link**
    action, the expiry, and **Copy code** and **Copy link** buttons. The raw code
    and link are not printed. The dialog watches the five-second status snapshot
    for a new device session or paired device and changes from **Waiting to
    connect** to **Connected** when enrollment succeeds. Closing while waiting
    cancels the unused code; closing after the dialog reports connected leaves
    the new device in place. An expired code offers **Create new link**. The
    guided-setup client step renders the same setup and pairing views inline.
    Review the browser client table and paired devices below. Harness adapter sessions
    are not listed here; they live under **Harness**. A one-time pairing session
    appears with a **Pairing** badge and no device until enrollment finishes; it
    is excluded from the active count and the local E2EE session count. Each
    paired session row shows the device's display name, short device id, and
    fingerprint so devices that share a label stay distinguishable.
    An active device's **Edit** action sets an alias of up to 64 characters; the
    enrolled label stays visible as secondary text, and clearing the alias restores
    the enrolled name. Connected clients resolve the same alias from the paired
    device list, so a rename applies on the next snapshot without reconnecting.
    Status badges call out degraded harness, relay, push, permissions, or
    missing files.
17. In **Traffic**, read the last minute's in and out rates, the request and
    error rates, the two sparklines for the last hour, and the totals since the
    window started. The card shows the local-versus-relay split, a peak minute,
    and the error breakdown. An amber **Spike** badge means the last complete
    minute was at least three times the previous half hour and above a floor; it
    is a hint, not a verdict.
18. Use the switch at the top left of **Traffic** to stop recording. The card
    collapses to its header, the counters are discarded, and the client table
    drops its traffic columns. Turning it back on starts a fresh window with a
    one-minute warm-up. The switch stays usable while external connections are off.
19. In **Activity**, read the in-memory events and the storage list. The storage
    header summarizes the most severe entry and its count, and the overview links
    here for the full list.
20. Use the **Orchestration** switch in **Settings** to start or stop the local
    orchestration service; the Overview tile still reports its state. Turning it
    on starts a detached local instance when nothing is answering and waits for
    `/health`; turning it off stops only the local instance started from this
    data directory. A Docker or external instance is detected and labelled, and
    the switch is disabled because the panel does not own it. The switch is the
    master gate for the feature; connected clients choose separately whether to
    use the orchestrator surface.
21. Leave the page open. It refreshes every five seconds while visible and
    pauses when the tab is hidden. Use **Refresh** for an immediate check.

## Core business rules

1. **Authenticated, and loopback by default.** The panel listens on
   `127.0.0.1:8790` by default. A container binds `0.0.0.0` inside its own
   network and publishes only on host loopback. Every API request except
   `/health`, the session endpoints, setup, and static assets requires a
   superadmin session. `CLARA_PANEL_BIND_HOST` and `CLARA_PANEL_ALLOW_REMOTE` are
   explicit exposure controls. The `Host`/`Origin` guard still expects a
   loopback origin, so remote access uses an SSH tunnel rather than direct LAN
   access. It is never served through the relay or Pages.
2. **First run blocks the hub.** With no owner account the panel serves only
   `/health`, static assets, `GET /panel/api/v1/session`, and
   `POST /panel/api/v1/setup`; every other panel API route returns
   `503 setup_required`. The local WebSocket, relay, harness probe and routing,
   push monitor, orchestration, and all pairing stay stopped until the owner is
   created. The setup form is local-only by default and needs no token. The
   handler creates the first user with a scrypt-hashed password, starts the
   transports in the same process, and returns a session cookie. A lost password
   is reset only by the host-side `clara-server admin reset`, which writes a
   fresh token and revokes sessions; there is no network password-reset
   endpoint. `CLARA_ADMIN_USERNAME` plus `CLARA_ADMIN_PASSWORD` or
   `CLARA_ADMIN_PASSWORD_FILE` creates the owner before startup for CI and
   headless installs. A host-supplied `CLARA_ADMIN_SETUP_TOKEN` requires a token
   on the setup form for an explicitly remote install.
3. **Reads and writes require a session.** `GET` and `HEAD` serve the snapshot
   and assets after login. `POST` is accepted at the feature, master-stop,
   monitoring, sync, orchestration, config, harness, browser-pairing, password,
   and device-purge routes; `PATCH` changes a device alias; `DELETE` revokes a
   device, cancels a browser pairing code, and removes a harness or the session.
   Unknown mutating methods return `405`.
4. **Secrets stay out of the snapshot.** The snapshot is built from an explicit
   allowlist. Device keys, enrollment codes, adapter credentials, the relay
   token, push endpoints, sync values, and file contents are never returned
   there. A one-time browser or adapter pairing code is returned only by the
   authenticated request that creates it. Device keys and unused enrollment
   tokens are encrypted at rest in SQLite with a key outside the database. The
   relay token is encrypted with the same key in `relay-credentials.json`; the
   URL and generated room stay in `server.json`. Device fingerprints, secret-configured flags, room
   id, and effective config values are included and start masked in the panel.
5. **Mutations are browser-hard to forge.** Besides authentication, the
   `Host`, `Origin`, and `Sec-Fetch-Site` checks, writes require
   `x-clara-panel: 1`; a write with a JSON body also requires
   `content-type: application/json`. Mutations reject unknown fields and cap the
   body at 8 KB. The custom header forces a CORS preflight for cross-origin
   pages, which the server rejects. No CORS headers are sent. Login and setup
   are rate-limited per source and username.
6. **Settings are durable.** Feature choices, the stopped flag, the monitoring
   choice, the orchestration switch, the client-sync gate and interval, the
   adapter-install switch, the panel users, and harness connections live in the
   hub's SQLite database and are loaded before any transport starts. The panel
   can fail without stopping the hub service; a busy panel port only loses the panel.
   The Web URL, adapter registry URL, and relay URL/room live in `server.json`, the VAPID contact in
   `vapid.json`, and the relay token in the encrypted `relay-credentials.json`; the
   panel writes all of them, the environment overrides any field, and the VAPID
   contact and relay target are applied live. The appearance choice is
   browser-local: it never reaches the hub service or its database.
   Adapter installs are off by default; they also require a loopback panel and a
   local hub process, so a containerized hub and a remote-exposed panel never
   receive SSH or Docker install actions. They still issue the copy code and
   command for the selected target, including the Docker-network address for a
   container on a containerized hub.
7. **Traffic monitoring is advisory and in memory.** The meter counts frame
   sizes, decrypted request actions, and the failures the hub already detects;
   it never reads or stores payloads. Counters live in a sixty-minute ring of
   one-minute buckets and reset on restart or when monitoring is switched off.
   Nothing is throttled, blocked, or persisted, and the per-client counters are
   hidden while monitoring is off.
8. **Sessions are read-only and fan out.** The Sessions view asks every paired
   harness for its newest non-archived sessions and active state; it does not add
   a second event stream or write session data. Rows are keyed by harness and
   session. An active session missing from the newest page is looked up by ID so
   older runaway work still appears. Offline, disabled, partial, and failed
   harnesses are reported separately without hiding the others. The endpoint is
   panel-only and is not part of the snapshot.
9. **Peek is presentation-only.** The eye button masks device ids and
   fingerprints, config and storage paths, local WebSocket endpoint, harness
   URL, relay URL and room, connection session ids, and WebSocket URLs in
   activity messages and error notices. The Home health tiles and status bar
   tooltips use the same scrubber. It does not redact the JSON snapshot, change
   any control, or reach the hub service: its allowlist remains the security
   boundary. The choice lives in `sessionStorage` for the tab, so a reload
   keeps it and a new tab starts masked.
10. **Guided setup is derived, and it does not auto-reopen after completion.**
    The modal derives completion from the live snapshot: the connection path is
    local, or the relay is online with an HTTPS Web URL; at least one harness is
    paired; and at least one non-revoked device is paired. The chosen path,
    dismissal, completion, and guide-seen timestamps live in `localStorage`; no
    hub setting or API changes. The modal opens automatically only while setup
    is incomplete and has not been dismissed. It never opens automatically after
    completion, even if a harness or device is later removed. **Settings → Setup**
    is the only restart surface: **Finish setup** while incomplete,
    **Reconfigure connections** and **Replay setup guide** after completion.

## Edge cases

- **No harness is configured** — **Pair Harness** opens the pairing modal, and
  harness-backed `/v1` requests return `503 harness_unconfigured` until an
  adapter is paired. The web can still connect and shows a harness banner.
- **Several harnesses are paired** — context-free catalog and info requests
  return `409 harness_required`; the web names a harness for every request.
- **The setup modal is skipped** — dismissal is stored on the browser. The
  modal stops auto-opening while setup is incomplete; **Settings → Setup →
  Finish setup** reopens it. Completion is still derived, so the badge and
  progress reflect whatever is paired.
- **Relay is selected but offline** — the connection step keeps **Continue**
  disabled. The user can start the relay, fix its token, or choose **Local
  only**. A relay path also requires an HTTPS Web URL; a loopback or HTTP URL
  keeps the step incomplete.
- **The local path keeps loopback** — setup can finish with
  `http://127.0.0.1:8080`. The client step warns that the link only works on
  this machine and points back to the Web URL field for another device.
- **External connections are off** — the connection step shows **Turn
  connections on**; the relay cannot come online until it succeeds. Turning
  connections on is the same master switch as the Hub card.
- **Relay is switched off** — the embedded Relay card stays collapsed until its
  toggle is on. The step explains that the switch must be enabled before the URL
  and token can be saved.
- **The harness is paired but offline** — the setup step shows
  **Paired · Offline** and allows continuing with a warning. The adapter can be
  started later; the hub keeps the credential.
- **A harness or device is removed after setup** — the modal does not reopen.
  **Settings → Setup** shows **Finish setup** again and the setup state becomes
  incomplete; the rest of the panel keeps working.
- **Local storage is cleared** — the path, dismissal, and guide-seen timestamps
  are lost. The modal may auto-open again, but completion is re-derived from the
  hub and the current pairings are not lost.
- **The adapter is paired but offline** — **Paired harnesses** says
  **Paired · Offline**, the probe is not run, and harness-backed `/v1` returns
  `harness_offline`. Start the adapter service; it reconnects automatically.
- **Harness access is disabled** — the page header and paired status say
  **Off**, the probe is not run, and proxied requests fail with a disabled
  error. Local and relay clients stay connected. The legacy harness feature gate
  has no switch in the Harness header because multiple harnesses are supported.
- **The adapter credential cannot be opened** — the connection stays listed but
  cannot authenticate. Re-pair the adapter; the rest of the hub keeps running.
- **No owner account exists** — the panel shows only the setup screen. The hub
  API returns `503 setup_required`, the local listener and relay do not start,
  and pairing commands refuse until the owner is created. The hub exits if the
  panel is disabled and no environment owner is configured.
- **The owner setup screen is opened remotely** — the panel's Host/Origin guard
  rejects it. Use an SSH tunnel or configure `CLARA_ADMIN_PASSWORD` before
  startup. A host-supplied setup token is the explicit remote setup path.
- **The setup token is wrong or expired** — setup returns a generic invalid-token
  error and keeps the form available. A token is only required when the host
  supplied one; local setup needs no token.
- **The superadmin password is lost** — run `clara-server admin reset`, or
  `docker exec clara-server /app/clara-server admin reset` for a container. It
  targets the running deployment, writes a new one-time token, and revokes every
  panel session. While that token
  is valid, the sign-in screen shows **Lost your password? Use a reset token**;
  the form takes the token and a new password and keeps the existing username.
  The link disappears when the token is used or expires. There is no HTTP reset
  route.
- **The environment owner is already configured** — the env values are ignored;
  the existing password is never overwritten. A partial username/password pair
  is ignored, and a password under 12 characters fails startup.
- **No owner and the panel is disabled** — startup fails with the missing
  account and the two supported paths (panel or `CLARA_ADMIN_PASSWORD`).
- **A local install and the Docker stack both have state** — the command refuses
  to guess and exits after printing the reason. Pass `--docker` for the
  `clara-server` container or `--local` for the local install.
- **The session expires** — the next poll returns `401`, the dashboard is
  replaced by the sign-in screen, and no stale data is shown.
- **The panel is reached through the Docker bridge** — `CLARA_PANEL_ALLOW_REMOTE`
  skips only the socket-address check; authentication, `Host`, `Origin`, and
  fetch-metadata checks still apply. Keep the published port on host loopback.
- **Local transport is off** — the card says off and the listener closes its
  clients with a clear reason. Turning it on starts a fresh listener.
- **Relay is not configured** — the relay card explains local-only mode and
  opens the relay editor. Saving a URL and hub token generates a room and
  connects without restarting the hub.
- **The relay room is regenerated** — every pairing code and signed grant tied
  to the old room becomes invalid; devices must pair again. The panel asks for
  confirmation first.
- **Relay settings come from the environment** — each field supplied by
  `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`, or `CLARA_AGENT_TOKEN` is read-only and
  wins over the panel value. Remove the variable and restart the hub service to
  edit that field here.
- **Relay reconnects** — the card shows the current state, last change, attempt
  count, and a redacted error.
- **Push is off or unavailable** — the card shows the saved choice, the
  effective state, the startup error, and the subscription count. Existing
  subscriptions are kept.
- **Client sync is off** — the web Sync tab disappears, sync actions return
  `disabled`, and the stored namespace and per-device category choices are kept
  for the next enable.
- **Sync interval changes** — connected clients receive the new cadence in a
  hub status update and reschedule their next check without reconnecting.
- **Connections are off** — a banner says external connections are off, every
  transport card shows a stopped state, feature switches are disabled, and
  **Pair Client** cannot create a code. An enabled feature switch turns red
  and a disabled one keeps its neutral track. The Traffic and Client sync
  switches keep their usual colors.
- **Orchestration changes** — the hub probes `/health` before and after the
  action, then broadcasts the new `orchestration` flag so connected clients
  update their feature availability without a reload. A failed local start keeps
  the error on the card. A Docker or external instance cannot be stopped from
  the panel.
- **A feature fails to start** — the saved choice remains, the card shows the
  error, and the rest of the hub keeps running.
- **No browser clients** — the client table shows an empty state and **Pair a
  browser** sits above it. A connected harness adapter still appears under
  **Harness → Connected adapters**.
- **A harness adapter is connected** — it has its own row under
  **Connected adapters** with its harness label, kind, short harness id, and
  credential fingerprint. It never appears in the Clients table or its counts.
  **Host resources** adds its CPU, memory, and adapter disk sample; a transient
  probe failure keeps the last sample for up to thirty seconds, and an adapter
  without the endpoint is not polled again until it reconnects.
- **No harness is paired** — **Sessions** explains that a harness must be added
  and shows no table rows.
- **Every harness is offline** — each harness card says **Offline**; the table
  says no paired harness is online and keeps the status cards visible.
- **One harness is offline or partial** — its card reports the state and error
  while sessions from other harnesses keep appearing. A partial harness still
  lists the rows it read.
- **Harness access is disabled** — every harness card says **Disabled** and the
  view reads no sessions. Sessions are not cached from an earlier enable.
- **A session is archived** — it stays hidden until **Show archived** is on. A
  snoozed session stays visible with a **snoozed** badge.
- **A running session is older than the newest page** — an active ID missing
  from the list is fetched by ID so the runaway row still appears.
- **A harness returns more sessions than the cap** — the table shows the newest
  rows up to the per-harness cap and marks the view **capped**.
- **A session disappears between requests** — its active lookup is ignored and
  the other rows remain.
- **The panel is screenshared** — session IDs, directories, parent IDs, and
  copy actions follow the header peek control.
- **A pairing session is listed** — the row carries a **Pairing** badge instead
  of a device. It is the one-time enrollment connection, not a failed client,
  and the hub retires it as soon as the device-enrolled response is sent.
- **A browser pairing code is cancelled or expires** — it cannot enroll a
  device. Create a new code; the cancelled token is removed immediately and an
  expired token is pruned on the next creation or pair command.
- **The panel is screenshared** — sensitive values load masked and the eye
  button reveals them for the tab. Masked values lose their full-value tooltips
  and copy buttons, and the same scrubber covers activity messages, error
  notices, Home health tiles, and status bar tooltips.
- **Monitoring is off** — the Traffic card collapses to its header and switch,
  the client table drops its traffic columns, and no counter moves. Turning it
  on starts a new window.
- **Monitoring is switched off mid-stream** — the counters stop where they are
  and the window is discarded. The stream itself keeps flowing.
- **The first minute after enabling or restarting** — the card says collecting
  and shows no rate or spike until one full minute has been measured.
- **A spike is detected** — the badge and notice name the signal that crossed
  the threshold. A large but legitimate stream raises it too.
- **A storage entry is unhealthy** — the storage header shows an error badge
  when any entry failed, otherwise a warning badge for read-only files, broad
  permissions, or missing required files. The tooltip counts each state.
- **Config permissions are broad** — storage warns when the database,
  `server.json`, `secrets.key`, `admin-setup.txt`, subscriptions, or VAPID keys
  are readable by other users.
- **The panel was not built** — the page returns a short instruction to run
  `pnpm build`; the JSON API still works.
- **Panel port is busy** — the hub service logs `panel unavailable` and continues.

## Out of scope

- Non-superadmin panel users and roles; the schema reserves a role column
- Remote access to the panel through the relay
- Editing the relay room as free text; rooms are generated by the hub and can
  only be regenerated. The panel does not edit other `server.json` fields beyond
  the Web URL, relay URL, and generated room
- Cloudflare Worker deletion, or attaching a hostname in a zone the token
  cannot manage
- A hub-wide active or default harness, or per-client selection in the panel
  header; paired harnesses keep serving the workspaces and sessions scoped to
  them
- Per-device relay targets; every device follows the hub's configured relay
- A sandbox for command execution, or an allowlist of every proxied API route
- Per-command arguments, wildcards, or regular expressions in the allowlist
- Rate limiting, blocking, or alerts driven by the traffic meter
- Historical metrics beyond the sixty-minute window, persisted logs, or an audit
  trail
- Reading, editing, or deleting individual synced values or namespaces from the
  panel; it controls only the global gate and cadence
- Steering, cancelling, archiving, or opening a session from **Sessions**; the
  view is read-only
- Per-session event counts, last event type, or a second event subscription
- Historical session search, full pagination, or cross-harness session totals

## Known gaps

- Authentication is not host isolation. A process with the panel cookie, the
  database, or `secrets.key` can still act as the hub; keep the config and
  data directories private.
- Sessions are in memory, so restarting the hub service signs everyone out.
- The superadmin password is hashed; adapter credentials are reversible and
  must be encrypted at rest with a backed-up key.
- Device identity is logical, not hardware-bound. The panel shows one row per
  stored device and one row per live connection; multiple tabs share a device.
- Traffic is measured at the hub, so connections the relay rejects before they
  reach it, and Cloudflare-level bandwidth, are visible only in Cloudflare
  analytics.
- The traffic window and the activity list are in memory and reset when the
  hub service restarts.
- **Sessions** reads up to 200 rows per harness by default, capped at 500, and
  does not paginate. Active sessions missing from that page are looked up up to a
  bound of 25 per harness. Last seen is the harness session update time, not an
  event count. The view can be up to five seconds stale while it polls.
- A session that spans a monitoring toggle shows only the traffic recorded while
  monitoring was on.
- Harness online counts come from live adapter sessions and can briefly lag a
  restart.
- The peek control hides values in the rendered panel only. The JSON snapshot
  still contains them, so browser devtools and the network panel can show them.
