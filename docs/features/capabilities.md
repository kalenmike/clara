| Orchestration    | Local loopback service and MCP bridge for package-based YAML/Markdown pipelines; the engine ships a default config that imports and routes the standard packages, and `CLARA_ENGINE_CONFIG` can name a custom `index.yml`; engine loads packages, pipelines, routers, agents, and scripts from data rather than built-in constants, ships standard software, content, and research packages, including a source-verified research pipeline that requires external search, dated source ledgers, and linked executive reports, resolves `std:software` package entries and the `std:software/feature`, `std:software/bug`, and `std:software/docs` pipelines with complete agent prompts, resolves a bare package id to its entry, renders route `criteria` into a `[ROUTES]` block in the router work-order prompt, snapshots and pins each run, and exposes `clara_start`, `clara_next`, `clara_complete`, `clara_fail`, `clara_route`, `clara_spawn`, `clara_status`, `clara_inbox`, and `clara_tick`; transitions are event-driven with token-bound leases, retries, background fail-fast groups, dynamic fan-out, an adapter that renews each step lease independently of model turns, and a watchdog that repairs stalls and expired leases through the same transition, settles every live step when a run ends, and rejects late worker calls; an agent that finishes without a control call gets one corrective turn before its final text is recorded as an inferred result; REST, SSE, and Streamable HTTP MCP run on `127.0.0.1:8789` with a bearer token; the service runs as a local host process beside the hub; the hub panel gates the feature and starts or stops a local instance, while status reports an externally managed engine without trying to control it; each client chooses whether to use the engine surface; the stdio bridge can auto-start the service; strict pipelines fail closed unless a harness adapter is registered, and the OpenCode adapter enforces tool, path, shell, turn, token, and violation policy while dispatching managed worker sessions, embedding the shared script runner (`@clara/runner`), and registering for the engine's configured workspace; terminal and alert deliveries are claimed atomically in the engine, so multiple adapter instances or overlapping polls cannot wake the origin more than once; every work order carries a resolved provider and model from its package or workspace, and the adapter pins each worker; the adapter installs a `clara` primary agent as the human-facing entry point, with a read-first intent policy, no repository tools, and only the orchestration tools it needs, so informational messages never create runs; model-facing `clara_start` takes only the request and always starts the active config's entry, while explicit targets stay in Clara Lab and operator tooling; the MCP installer keeps a separate `/pipeline <request>` command for manual work-order mode; the adapter adopts non-terminal runs after a restart and delivers new alerts and finished root runs into the origin session; the service records the root origin and exposes status, inbox, and SSE                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

| Budgets          | Turn, tool-call, wall-clock, and attempt limits are hard caps in every enforcement mode, including `observed`; an exhausted budget denies further work tools but keeps the Clara control tools available, records one `budget.exhausted` event per attempt, reserves the final 8% of the token budget (capped at 10k tokens) for the worker's report, keeps a valid result that arrives over budget instead of retrying the step, and retries a step that opts into `limits.on_exhausted: fail` when a budget denial cut the worker short, carrying its partial result into the next attempt. The OpenCode adapter reports model token usage from assistant-message events, so token budgets are enforced for managed workers too; it caps managed tool results at 48k characters with a truncation marker, reports a cache-weighted budget total so long sessions are not cut off by re-read context, and the software bug lifecycle grows retry budgets while bounding attempts. Other harnesses must report usage through `clara_usage`. ## Adapter installation

`@clara/adapter-opencode` is the standalone OpenCode adapter. Its installer
writes the OpenCode binding, registers the MCP bridge when asked, and installs
one shared standalone runner per workspace. `@clara/adapter-runtime` is the
harness-neutral runtime that the adapter imports; it has no OpenCode logic.
The OpenCode binding installs a `clara` primary agent and disables the plugin's
embedded runner so the shared runner is the only script executor. Agent and
router claims are scoped to the harness that owns the run or the adapter pinned
by `requires.adapter`; script claims stay shared so one runner serves every
harness in the workspace.

## Partial

- **Clara Lab** previews files on the lab host and probes through the running
  service. The host path is editable in Settings, including through a native
  folder picker; the service reports its own workspace. A containerized service
  with a different mount can still differ. Targets are enumerated for the root
  package and its direct imports, and source view caps at 512 KB.
- **Session list** returns the newest 50 sessions; there is no infinite scroll.
- **Chat history** loads the newest 100 messages first and fetches older pages
  as the conversation is scrolled toward the top.
- **Command preview** shows only the name and description because the server does
  not expose command templates.
- **Plan** reads the newest completed `todowrite` tool call. The OpenCode adapter
  requires the server to enable the experimental todo tool (`experimental.todo`) or the section
  stays empty and Request Plan cannot create a list. Forked sessions hide the
  parent's checklist client-side; the copied call cannot be removed from the
  transcript.
- **Mentions** insert `@path` text references; they do not upload file contents.
- **Git changes** are read-only statistics for the working tree, the last three
  commits, or the branch base; there is no patch review.
- **Connection** holds one server at a time; there are no saved profiles.
- **Remote access** broadcasts each hub frame to every client in the room;
  there is no per-client routing or message backlog.
- **Pairing** gives each device its own revocable key and uses a one-time
  enrollment token plus a ten-minute relay enrollment grant. Each device or
  adapter then holds a thirty-day grant refreshed on each connect; v4 requires
  every existing device and adapter to pair once more. Revoking a device removes
  its key, live sessions, push subscriptions, and future grant refreshes.
- **Push** requires the hub and a browser push endpoint; it does not
  replay events missed while the hub is down.
  Mobile devices are held while a visible desktop client is recently active, and
  there is no manual "send to phone" override.
- **E2EE** uses per-session P-256 ECDH for forward secrecy; each device key
  protects that device's sessions, and a recorded session cannot be rebuilt from
  a later key compromise.
- **Git history** runs one fixed `git log -n 10` with a machine-readable
  `--format` in the session's directory through the hub's `/v1/git/log`
  endpoint. Rows preview conventional headers and expand to the author date,
  author, co-authors, and message body. The browser has no generic shell path.

## Not built

- Pairing expiration, one-time codes, or scanning a QR from a saved screenshot
- Per-device keys or revocation
- Message backlog or offline delivery
- Full diff review, staging, committing, worktree management, interactive
  PTY/terminal sessions, MCP and plugin management. The pair terminal is a
  read-only emulation, not an interactive shell.
- A sandbox for command execution, or a positive allowlist of every proxied
  harness route
- Simultaneous connections to multiple hubs
- Session sharing, export, or import
- Per-project or per-kind push filtering
- Fetching OpenCode Go allowance or remaining usage limits
- A namespace picker, per-device namespaces, or a conflict-resolution UI for
  client settings sync
