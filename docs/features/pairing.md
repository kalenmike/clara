# Pairing

## Summary

Pairs a browser or installed PWA with a Clara home agent without exposing the
OpenCode password or the E2EE key to Cloudflare. The phone scans the terminal QR
with its camera or pastes the same code, and Clara stores the device
configuration locally.

## User flow

1. Start the home agent (`clara-server serve` or the systemd unit).
2. Run `clara-server pair` on the machine that runs the agent. The terminal
   prints a QR code, a `https://clara.kalenmichael.com/#pair=…` link, a
   `clara1_…` code, and the key fingerprint. Add `--local` to force a local-only
   code even when the agent has a relay configured.
3. Open Clara on the device. **Pair this device** offers **Scan QR code** and a
   paste field. Tapping Scan opens the rear camera and connects as soon as a
   Clara QR is recognized; a `clara1_…` code or `#pair=` link can still be
   pasted. Opening a pairing link directly is consumed automatically and shows a
   branded connecting splash.
4. Clara validates the payload, connects to the full WebSocket URL, completes
   the E2EE handshake, and calls the OpenCode info endpoint through the tunnel.
5. On success the device is stored and Clara opens the last project. The
   Settings → Server card shows the relay state and fingerprint-backed session.
   On failure Clara returns to the pair form and shows the reason.
6. **Settings → Disconnect** clears the stored pairing, disables push on this
   device, and returns to the connect screen.
7. Run `clara-server pair --rotate` to invalidate every paired device, clear
   stored push subscriptions, and print a new code. Restart the home agent so it
   loads the rotated key.

## Core business rules

1. Pairing is the only way to obtain the PSK and relay client token. They are
   never bundled into the Pages build.
2. The pairing payload contains the full WebSocket URL, room id, client token,
   PSK, and fingerprint. The URL fragment is not sent to Pages or Cloudflare.
3. Camera scanning runs entirely in the browser: frames are decoded on the
   device and never reach Pages, the relay, or the home agent. A QR that does not
   decode to a Clara payload is rejected before pairing.
4. `VITE_CLARA_WS_URL` is the relay deployment switch. When set it supplies the
   relay endpoint for room-scoped payloads; a `local` payload always keeps its
   own URL because it was generated by an agent without a relay. When empty the
   pairing payload's URL is used.
5. A local pairing code is local-only: the web client never rewrites it to the
   relay, and an HTTPS page cannot open its `ws://` socket. `clara-server pair
--local` forces such a code even when the agent has a relay configured; the
   local listener runs alongside the relay client.
6. A device is stored in `localStorage` after pairing; direct connections keep
   the existing session/local-storage remember rule.
7. The fingerprint shown by the web must match the terminal fingerprint before
   the connection is trusted.
8. One PSK and one client token are shared by all paired devices in v1.

## Edge cases

- **Invalid or truncated code** — the form reports a pairing-code error and
  keeps the input.
- **Camera permission denied** — the scanner explains how to allow access,
  including iPhone Settings → Clara → Camera. Paste still works.
- **No camera or camera busy** — the scanner names the condition and offers
  paste instead.
- **Insecure page** — browsers only open the camera on HTTPS or localhost, so
  the scan action is hidden on a plain `http://` address; paste still works.
- **Non-Clara QR** — the scanner reports that the code is not a Clara pairing
  code and keeps looking instead of starting a connection.
- **Blurred or distant QR** — the scanner keeps sampling frames; the code must
  be close enough to resolve before anything is paired.
- **Pairing link fails** — the connecting splash gives way to the pair form,
  which shows the relay, handshake, or fingerprint failure.
- **Fingerprint mismatch** — the transport closes with `4001`; the connect
  screen reports a key mismatch and asks for a fresh code.
- **Relay offline** — the device connects but the agent is absent; the client
  closes with `1013` and the form reports a connection failure.
- **Wrong relay token** — the Worker returns `401` before the upgrade.
- **Agent restart** — the DO closes clients with `1012`; the web reconnects and
  re-handshakes automatically.
- **Rotated key** — old devices fail the fingerprint check and must re-pair.
- **Local-only pairing** — the code points at `ws://127.0.0.1:8788/ws`; it only
  works on the same machine, and an HTTPS page reports that the code is
  local-only. `clara-server pair` warns when the pairing link is remote while the
  agent has no relay. Configure the relay for phones.
- **Local code with a relay configured** — `clara-server pair --local` emits room
  `local` and the listener URL without needing relay tokens; the web keeps that
  endpoint, so the code still works on this machine only.
- **Deployment switch changed** — a relay pairing is re-resolved against
  `VITE_CLARA_WS_URL` on boot, so existing devices follow the new endpoint; a
  `local` pairing keeps its own URL.
- **Cleared browser storage** — the device is forgotten; pair again.
- **Pairing link opened by mistake** — the fragment is consumed and stored
  immediately; use Disconnect to remove it.

## Out of scope

- Per-device keys or per-device revocation
- Pairing expiration windows or one-time codes
- Scanning a QR from a saved screenshot or photo
- Torch, camera switching, or barcode formats other than QR
- Multiple home agents or saved pairing profiles

## Known gaps

- A pairing code can be reused until the PSK is rotated.
- The client token is shared by every paired device.

## Technical appendix

<details>
<summary>Routes, data, and references</summary>

- Pair command: `node apps/server/dist/index.js pair [--rotate] [--local] [--no-qr]`
- Pairing URL: `<pairingBaseUrl>/#pair=<base64url(JSON)>`
- Payload: `{ v, wsUrl, room, clientToken, psk, fingerprint }`
- Scanner: `getUserMedia` with the rear camera, `jsqr` loaded on demand, frames
  decoded on a detached canvas; the stream stops on detection or close
- Camera policy: `Permissions-Policy: camera=(self)` in
  `apps/web/public/_headers`; self-hosted deployments must send the same header
- Storage key: `clara.connection.local` / `clara.connection.session`
- Connect screen: `/connect`
- Server config: `~/.config/clara/server.json` (mode `0600`)
- Push subscriptions: `~/.config/clara/subscriptions.json`, cleared by
  `pair --rotate`
- Related: [E2EE](../architecture/e2ee.md), [Relay](../architecture/relay.md)

</details>
