# Pairing

## Summary

Pairs a browser or installed PWA with a Clara hub without exposing the harness
password to Cloudflare. Each device receives its own revocable key
through a one-time enrollment link. The host creates the link, code, or QR from
the hub panel or the pairing command; the phone scans the QR with its camera or
pastes the same code, and Clara stores the device credential locally.

## Harness adapter pairing

The panel also pairs harness adapters with the same one-time-code and E2EE
pattern. **Harness → Add harness** chooses the adapter type and install method
(SSH, Docker, or Manual) and produces a `clara-harness1_…` code. SSH and Docker
run the registry install script on the target; Manual copies the code and
command. For the included adapters the manual command is
`clara-adapter-opencode install --pair <code>` or
`clara-adapter-claude install --pair <code>` (or
`pnpm clara adapter install --opencode --pair <code>` /
`--claude` in the repository). It discovers the harness, enrolls the adapter
over the local or relay WebSocket, and stores its long-lived credential. The adapter reconnects with that
credential and never exposes an inbound port. Reinstall and re-pair reuse the
stable harness identity, so Clara session and project metadata stays attached.
Adapter codes cannot enroll a browser: the connect screen names them and points
at the panel's **Clients → Pair Client** action or `clara-server pair`.

## User flow

1. Start the hub (`pnpm clara server start` or the systemd unit).
2. Sign in to the hub panel and choose **Clients → Pair Client**, or run
   `clara-server pair` on the machine that runs the hub service. Both paths
   produce a QR code, a web link, a `clara1_…` code, and an enrollment
   fingerprint. The panel offers a **Relay | Local** choice when a relay is
   configured; the command takes `--no-relay` for the same local result. The
   dialog moves from the transport choice to a QR, an **Open Link** action, the
   expiry, and **Copy code** and **Copy link** buttons. It shows **Waiting to
   connect** until a device enrolls, then **Connected**. Closing before
   enrollment cancels the unused code; closing after it leaves the new device in
   place. Local codes use the panel Web URL (default
   `http://127.0.0.1:8080/#pair=…`); relay codes use the same Web URL.
3. Open Clara on the device. **Pair this device** offers **Scan QR code** and a
   paste field. Tapping Scan opens the rear camera and connects as soon as a
   Clara QR is recognized; a `clara1_…` code or `#pair=` link can still be
   pasted. Opening a pairing link directly is consumed automatically and shows a
   branded connecting splash.
4. Clara validates the payload and expiry, checks that this browser can store a
   non-extractable key, connects with the one-time enrollment token and, for a
   relay code, its one-time enrollment grant, and enrolls the device.
5. The hub stores the device key encrypted at rest, consumes the token, and
   returns the device id, fingerprint, and first thirty-day device grant. Clara
   stores the non-extractable key in IndexedDB, keeps the grant for relay
   connects, reconnects with the device id, and probes the hub API. Harness
   information loads separately through the default harness.
6. On success Clara opens the last project. The Settings → Server card shows the
   relay state and device identity. On failure Clara returns to the pair form and
   shows the reason.
7. **Settings → Disconnect** clears the stored device from this browser and
   returns to the connect screen. The device stays in the panel until it is
   revoked there.
8. Run `clara-server pair --revoke-all` from the host to revoke every device and
   clear push subscriptions. Use `clara-server pair --revoke <deviceId>` for one
   device. The panel is the immediate revocation surface.

## Core business rules

1. Pairing is the only way to obtain a device credential. No encryption key is
   bundled into the Pages build.
2. A pairing payload contains the WebSocket URL, room id, a public enrollment
   id, a one-time enrollment token, the token fingerprint, and the expiry. A
   relay payload also carries a ten-minute signed enrollment grant scoped to
   that id; a local payload carries no grant. The fragment is not sent to Pages
   or Cloudflare.
3. The enrollment token and its grant are valid for 10 minutes and enroll
   exactly one device. A device retry with the same device id is idempotent; a
   different device reusing the token is rejected.
4. Camera scanning runs entirely in the browser: frames are decoded on the
   device and never reach Pages, the relay, or the hub. A QR that does not
   decode to a Clara payload is rejected before pairing.
5. `VITE_CLARA_WS_URL` is the relay deployment switch. When set it supplies the
   relay endpoint for room-scoped payloads; a `local` payload always keeps its
   own URL because it was generated by a hub without a relay. When empty the
   pairing payload's URL is used. The panel **Web URL** is used for relay links
   and defaults to `http://127.0.0.1:${CLARA_WEB_PORT:-8080}`;
   `CLARA_PAIRING_BASE_URL` overrides it. A local-only code, from the panel
   option or `--no-relay`, uses a loopback link when the configured Web URL is
   remote; other local codes keep the configured Web URL.
6. A local pairing code is local-only: the web client never rewrites it to the
   relay, and an HTTPS page cannot open its `ws://` socket. The panel's **Local
   connection only** option or `clara-server pair --no-relay` forces such a code,
   uses the local web app link, and works even when the hub has a relay
   configured; the local listener runs alongside the relay client.
7. The device key is stored as a non-extractable `CryptoKey` in IndexedDB. Raw
   key bytes are never written to `localStorage`.
8. The fingerprint shown by the web should match the fingerprint in the panel's
   paired-devices table or printed by the pairing command before the enrollment
   is trusted.
9. Each device has its own key and can be revoked independently. A revoked
   device's record can then be deleted permanently from the panel.

## Edge cases

- **Invalid or truncated code** — the form reports a pairing-code error and
  keeps the input.
- **Expired code** — Clara rejects it before connecting and asks for a fresh
  code from the panel or `clara-server pair`.
- **Code already used** — the hub rejects enrollment with a used-code error.
  Generate a new code; the first device is listed in the panel.
- **Camera permission denied** — the scanner explains how to allow access,
  including Settings → Safari → Camera on iPhone (home-screen apps share
  Safari's permission). Paste still works.
- **No prompt on iPhone** — Clara requests the camera before loading anything
  else and reports the step that stalled after a deadline instead of waiting
  forever. The message names Settings → Safari → Camera, and offers retry or
  paste.
- **Camera opened but no picture** — a granted stream that never delivers frames
  (common after an iPhone app resumes) is reported after eight seconds with the
  close-and-reopen or restart advice instead of showing a black preview.
- **Scanner backgrounded** — leaving the app stops the stream; returning
  rebuilds the video element and starts the camera again, because iOS can leave
  the resumed pipeline dead.
- **Camera stops mid-scan** — an unexpectedly ended track reports that the
  camera stopped and offers another attempt; closing the scanner still releases
  the camera.
- **No camera or camera busy** — the scanner names the condition and offers
  paste instead.
- **Insecure page** — browsers only open the camera on HTTPS or localhost, so the
  scan action is hidden on a plain `http://` address; paste still works.
- **Non-Clara QR** — the scanner reports that the code is not a Clara pairing
  code and keeps looking instead of starting a connection.
- **Blurred or distant QR** — the scanner keeps sampling frames; the code must
  be close enough to resolve before anything is paired.
- **Pairing link fails** — the connecting splash gives way to the pair form,
  which shows the relay, handshake, or enrollment failure.
- **Fingerprint mismatch** — the transport reports the mismatch and asks for a
  fresh code.
- **Relay offline** — the device connects but the hub is absent; the client
  closes with `1013` and the form reports a connection failure. Confirm the
  pairing room matches the relay card in the hub panel.
- **Expired or invalid enrollment grant** — the Worker returns `401` before the
  upgrade; generate a fresh pairing code.
- **Hub restart** — the DO closes clients with `1012`; the web reconnects and
  re-handshakes automatically with the stored device key.
- **Device revoked** — the next handshake or action receives `revoked_device`;
  the client disconnects and the panel shows the device as revoked. Delete the
  revoked record when it is no longer useful for auditing; later connections
  are then rejected as an unknown device.
- **Browser cannot store a protected key** — Clara refuses to consume the code
  and explains that the browser cannot persist a non-extractable key.
- **Local-only pairing** — the code points at the live local listener URL,
  usually `ws://127.0.0.1:8788/ws`; it only works on the same machine, and an
  HTTPS page reports that the code is local-only. The panel and
  `clara-server pair` warn when the pairing link is remote while the hub has no
  relay. Configure the relay for phones.
- **Relay URL without the hub token** — the hub still starts and creates a local
  pairing code. The panel Relay card marks the token as missing; save it there
  before creating a relay code.
- **Local code with a relay configured** — the panel's **Local** choice, or
  `clara-server pair --no-relay`, emits room `local`, the listener URL, and the
  local web app link without a relay grant; the web keeps that endpoint, so the
  code still works on this machine only.
- **Deployment switch changed** — a relay pairing is re-resolved against
  `VITE_CLARA_WS_URL` on boot, so existing devices follow the new endpoint; a
  `local` pairing keeps its own URL.
- **Cleared browser storage** — the device is forgotten; generate a new code and
  pair again. Revoke the old entry if it will not be used.
- **Pairing link opened by mistake** — the fragment is consumed and the device
  is enrolled; revoke it in the panel if it was not intended.

## Out of scope

- Per-device relay targets; every device uses the hub's configured relay
- Pairing expiration windows longer than the enrollment token and grant
- Scanning a QR from a saved screenshot or photo
- Torch, camera switching, or barcode formats other than QR
- Multiple hubs or saved pairing profiles
- Panel approval of new devices

## Known gaps

- A stolen but unused pairing link can enroll one device until it expires or is
  used. The panel shows the new device and can revoke it.
- A relay device grant lasts thirty days and is refreshed on each connect. A
  device offline longer than that must pair again.
- The device id and grant id are visible to the relay, which can correlate a
  device's connections.

## Technical appendix

<details>
<summary>Routes, data, and references</summary>

- Pair command: `node apps/hub/server/dist/index.js pair [--no-relay] [--no-qr] [--revoke-all] [--revoke <id>]`
- Panel pairing: `POST /panel/api/v1/devices/pairings` with `{ "localOnly": true }`
  creates a code; `DELETE /panel/api/v1/devices/pairings/:id` cancels one. Codes
  are returned only from the authenticated creation request, not in the status
  snapshot.
- Pairing URL: `<webUrl>/#pair=<base64url(JSON)>`
- Payload: `{ v, wsUrl, room, enrollId, enrollToken, grant?, fingerprint, expiresAt }`;
  `grant` is required for a relay payload and absent for a local one
- Scanner: `getUserMedia` is requested first, with `jsqr` loaded in parallel on
  demand; frames are decoded on a detached canvas and the stream stops on
  detection or close. Camera start, decoder load, and first-frame paint each
  have a deadline, the dialog names the current step, and every attempt gets a
  fresh `<video>` element because iOS can wedge a stopped one
- Camera policy: `Permissions-Policy: camera=(self)` in
  `apps/web/public/_headers`; self-hosted deployments must send the same header
- Storage: IndexedDB `clara-devices` / `device`; no connection secret in
  `localStorage`
- Connect screen: `/connect`
- Server config: `~/.config/clara/server.json` (mode `0600`); the panel writes
  `pairingBaseUrl` there and `pair` reads it without opening SQLite for the Web
  URL, then opens SQLite to create the enrollment token
- Device keys: `devices` and `device_keys` in SQLite, encrypted with
  `secrets.key`. `devices.label` is the enrolled name captured at pairing and is
  immutable; a nullable panel-set `devices.alias` overrides only the displayed
  name.
- Pairing tokens: `pairing_tokens` in SQLite, encrypted with `secrets.key`
- Adapter pairing: `harness_pairings`, `harness_identities`, and
  `adapter_credentials`; adapters use the same E2EE handshake and sealed frames
  as browser devices
- Push subscriptions: `~/.config/clara/subscriptions.json`, tagged with the
  device id and removed when that device is revoked
- Related: [E2EE](../architecture/e2ee.md), [Relay](../architecture/relay.md)

</details>
