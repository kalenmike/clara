# Relay

The relay lets a browser or installed PWA reach a Clara hub that is not
publicly reachable. The hub opens one outbound WebSocket to Cloudflare; the
browser opens one inbound WebSocket to the same room. Cloudflare only forwards
opaque frames.

```text
OpenCode HTTP/SSE
      ▲
      │ basic auth (server-side)
      ▼
Clara hub /v1 API ──outbound WSS──▶ Worker ──▶ RelayRoom DO ◀──WSS── browser / PWA
      │                                              │
      └──────────── E2EE payloads ───────────────────┘
```

## Components

| Component       | Location                | Responsibility                                               |
| --------------- | ----------------------- | ------------------------------------------------------------ |
| Hub service     | `apps/server`           | Hub `/v1` API, harness auth, E2EE sessions, relay reconnect  |
| Relay Worker    | `workers/relay`         | Path routing, subprotocol/token auth, static health endpoint |
| `RelayRoom` DO  | `workers/relay`         | One hub socket + N client sockets; frame forwarding only     |
| Web transport   | `apps/web`              | Fetch-over-WebSocket shim, E2EE, reconnect, heartbeat        |
| Shared protocol | `packages/shared-types` | Frame/action/state types and pairing payloads                |
| Crypto          | `packages/crypto`       | device-key derivation, AES-GCM seal/open, replay guard       |

## Example domain layout

| Host            | Service                                  |
| --------------- | ---------------------------------------- |
| `clara.example` | Cloudflare Pages project for the web app |
| `relay.example` | Worker custom domain route for the relay |

The Worker route is `/room/:roomId`. The room id is a 128-bit base64url value
generated by the hub and stored in `~/.config/clara/server.json`. It is
not a secret, but it is unguessable.

## Room behavior

- A room has exactly one hub socket. A new hub connection closes the old
  one with code `4002` and closes clients with `1012` so they re-handshake
  against the new process.
- Client frames go only to the hub. Hub frames are broadcast to every
  client. There is no per-client routing state in the DO.
- Each client uses its own `sid` and per-session keys. The hello also carries a
  stable `deviceId`, so the relay can correlate connections from one device
  even though the `sid` is fresh. Foreign frames fail to decrypt and are
  dropped; the relay does not need to understand them.
- When the hub disconnects, clients close with `1012` and reconnect with
  jittered backoff.
- When no hub is present, a client frame closes that client with `1013`.
- No message backlog, storage, alarms, or CRDT state. A mobile client that
  resumes after a gap reconnects and invalidates its cached queries.
- The DO uses WebSocket hibernation and has no Durable Object storage bindings.

## Authentication

Browsers cannot send an `Authorization` header on a WebSocket, so auth travels
in `Sec-WebSocket-Protocol`:

```text
clara.v1
clara.role.client | clara.role.agent
clara.auth.<token>
```

The Worker checks the role-specific token with a constant-time comparison, then
forwards a trusted `x-clara-role` header to the DO. Use separate secrets:

```bash
cd workers/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
pnpm exec wrangler secret put CLARA_CLIENT_TOKEN
```

The client token is embedded in the pairing payload. It prevents unpaired
traffic from reaching the hub, but it is not the encryption key. An attacker
with the client token and no device key can open sockets and cause noise; they cannot
read or forge E2EE frames. Rotate both tokens if either leaks.

The hub's relay role and secret keep the historical `agent` name
(`clara.role.agent`, `CLARA_AGENT_TOKEN`), while prose calls that side the hub.

## Deployment

1. Create the Pages project and custom domain; build with
   `pnpm --filter @clara/web build` and output `apps/web/dist`.
2. Set `VITE_CLARA_WS_URL=wss://relay.example` in the Pages build environment,
   using your own relay host.
3. Deploy the Worker with `pnpm deploy:relay`; it creates the DO namespace. Add
   your own custom domain route in `workers/relay/wrangler.jsonc` or the
   Cloudflare dashboard, or use the workers.dev URL.
4. Set the Worker secrets and matching server environment variables. Open the
   hub panel and set **Web URL** to your web URL; `CLARA_PAIRING_BASE_URL`
   overrides it if you prefer environment configuration.
5. Start the hub with `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`,
   `CLARA_AGENT_TOKEN`, and `CLARA_CLIENT_TOKEN`. When the room is omitted, the
   hub generates one and persists it in `server.json`; keep that value stable,
   because every pairing code is scoped to it.
6. Run `node apps/server/dist/index.js pair` and scan the QR from the phone.

## Failure behavior

| Failure                   | Result                                                                     |
| ------------------------- | -------------------------------------------------------------------------- |
| Relay unreachable         | Hub retries with exponential backoff (1s–30s, jittered).                   |
| Hub offline               | Clients connect, then close with `1013`; the connect screen shows failure. |
| Hub restarts              | DO closes clients with `1012`; both sides re-handshake.                    |
| Wrong token               | Worker returns `401` before upgrading.                                     |
| Unknown or revoked device | Hub sends an `error` frame; the client reports and stops reconnecting.     |
| Version mismatch          | Handshake is rejected; update web and hub together.                        |
| Slow client               | DO closes above the buffered-output threshold.                             |
| Many clients              | Egress scales with client count because hub frames are broadcast.          |
