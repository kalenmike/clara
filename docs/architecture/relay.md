# Relay

The relay lets a browser, installed PWA, or harness adapter reach a Clara hub
that is not publicly reachable. The hub opens one outbound WebSocket to
Cloudflare; browsers and adapters open inbound WebSockets to the same room.
Cloudflare only forwards opaque frames.

```text
Harness ──HTTP/SSE──▶ adapter ──outbound WSS──▶ Worker ──▶ RelayRoom DO ◀──outbound WSS── hub
                                                                    ▲
                                                                    └──WSS── browser / PWA
```

In local mode an adapter opens the hub's local WebSocket directly instead of
joining the relay room.

## Components

| Component       | Location                          | Responsibility                                                               |
| --------------- | --------------------------------- | ---------------------------------------------------------------------------- |
| Hub service     | `apps/hub/server`                 | Hub `/v1` API, adapter routing, E2EE sessions, peer binding, relay reconnect |
| Adapter         | `apps/adapters/*`                 | Harness translation, harness auth, adapter E2EE and reconnect                |
| Relay Worker    | `infra/relay`                     | Path routing, subprotocol/grant auth, static health endpoint                 |
| `RelayRoom` DO  | `infra/relay`                     | One hub socket + N client sockets; peer tagging, limits, forwarding          |
| Web transport   | `apps/web`                        | Fetch-over-WebSocket shim, E2EE, reconnect, heartbeat                        |
| Shared protocol | `packages/contracts/shared-types` | Frame/action/state types and pairing payloads                                |
| Crypto          | `packages/crypto`                 | device-key derivation, AES-GCM seal/open, replay guard                       |

## Example domain layout

| Host            | Service                                  |
| --------------- | ---------------------------------------- |
| `clara.example` | Cloudflare Pages project for the web app |
| `relay.example` | Worker custom domain route for the relay |

The Worker route is `/room/:roomId`. The room id is a 128-bit base64url value
generated by the hub and stored in `~/.config/clara/server.json`. It is
not a secret, but it is unguessable. The panel never accepts a room as text; it
only regenerates a fresh random value.

## Room behavior

- A room has exactly one hub socket. A new hub connection closes the old
  one with code `4002` and closes clients with `1012` so they re-handshake
  against the new process.
- Browsers and adapters are both clients of the room. The DO assigns each client
  socket a random peer id and keeps it in the socket attachment, so it survives
  hibernation. Every client frame is wrapped in a route envelope that carries
  that peer id before it reaches the hub. Hub frames are broadcast to every
  client unchanged. The DO holds no per-session routing state: the hub binds
  each session to the peer that opened it.
- Each client uses its own `sid` and per-session keys. The hello also carries a
  stable `deviceId` for a browser or a stable adapter identity for an adapter, so
  the relay can correlate connections from one peer even though the `sid` is
  fresh. Foreign frames fail to decrypt and are dropped; the relay does not need
  to understand them.
- A room admits at most 32 client sockets, and at most 8 of those from one
  `cf-connecting-ip` address. The signed grant kind selects the per-peer budget:
  a browser grant gets 60 frames/s and 512 KiB/s, while an adapter grant gets
  600 frames/s and 4 MiB/s because one adapter socket carries every proxied
  browser request and event stream. Both use a one-second frame burst and a
  two-second byte burst, and any client frame over 128 KiB is refused. A refusal
  closes the socket with `4008` and a reason that names the limit, or with
  `4009` for an oversized frame. No later frame from that socket is forwarded,
  so the hub never sees a hole in the sealed sequence.
- When the hub disconnects, clients close with `1012` and reconnect with
  jittered backoff.
- When no hub is present, a client frame closes that client with `1013`.
- No message backlog, storage, alarms, or CRDT state. A mobile client that
  resumes after a gap reconnects and invalidates its cached queries.
- The DO uses WebSocket hibernation and has no Durable Object storage bindings.

## Authentication

Browsers cannot send an `Authorization` header on a WebSocket, so auth travels
in `Sec-WebSocket-Protocol`:

```text
clara.v1
clara.role.client | clara.role.agent
clara.auth.<hub token | grant>
```

The hub presents the shared `CLARA_AGENT_TOKEN`; every browser and adapter
presents a per-device signed grant. The Worker checks the agent token by
comparing digests in constant time and verifies each client grant's signature,
room, role, lifetime, and id before upgrading the socket. It then forwards a
trusted `x-clara-role` header and, for clients, tags every frame with the
verified grant id. Set only the hub secret:

```bash
cd infra/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
```

A grant is not an encryption key. It gates relay socket access for exactly one
device, adapter, or enrollment, and it carries no key material. The hub still
binds each session to the peer that opened it: it serves a hello or sealed frame
only from that peer, so a guessed `sid` cannot kill or hijack a session. Every
client frame arrives wrapped in a route envelope that names the sender's peer
and grant id, so the hub never treats the payload's `sid` as proof of ownership.
A leaked grant can open a socket and add noise, but cannot read or act without
the matching device or adapter key; revocation stops refreshes and the grant
expires on its own. The grant format, TTLs, and verification rules live in
[Handshake v4](../features/handshake-v4.md#relay-grant-encoding-and-verification).
The adapter adds its own long-lived credential after enrollment.

The hub token must be 32–512 characters with no whitespace and no comma. The
panel refuses to save anything else and names the rule, because a comma would
split the subprotocol header, and deployment checks the same shape. The Worker
hashes the presented and configured tokens and compares the digests, so a wrong
length is no cheaper to probe than a wrong value. Malformed room escapes are
refused with `400` instead of reaching the DO, and the Worker strips the
`clara.auth.*` values before forwarding, so the DO never sees a token or grant.

The hub's relay role and secret keep the historical `agent` name
(`clara.role.agent`, `CLARA_AGENT_TOKEN`), while prose calls that side the hub.

## Hub token compromise

Two hubs that present the same hub token to the same room evict each other: the
DO keeps one hub socket, so every connection closes the previous one with
`4002`. The replaced hub waits at least 30 seconds, records the replacement, and
the Relay card shows a warning instead of treating `4002` as an ordinary
disconnect. With a leaked token the two sides ping-pong indefinitely and remote
clients look flaky.

Symptoms:

- The Relay card repeatedly reports **Another hub connected to this room**.
- The relay reconnects about every 30 seconds or more, and remote clients
  disconnect at the same time.
- The hub log shows `relay disconnected (4002 ...)` followed by the replacement
  warning.

Immediate steps:

1. Find the second hub process using this room and token. Check other machines,
   old containers, and a second copy of the hub started from a different config
   directory, then stop it. Confirm that only one hub process serves this room.
2. Rotate the Worker secret, keeping the same value on the hub:

   ```bash
   cd infra/relay
   pnpm exec wrangler secret put CLARA_AGENT_TOKEN
   ```

   Then enter the same value in the panel's **Relay** card, or deploy the relay
   again from the panel, which writes the token. Saving the card applies the new
   token without a hub restart and clears the replacement warning.

3. Watch the Relay card until it stays online and the warning does not return.
4. If the Cloudflare API token may have leaked, rotate it in Cloudflare and
   update the panel's saved deployment token.

A hub-token rotation does not require devices to pair again: grants are signed
by the Worker and the hub keeps the same room. Devices pair again only when the
relay URL or the room changes.

## Relay version

The DO advertises `x-clara-relay-version: 3` on the upgrade response and speaks
route envelope v3. Envelope v3 carries the verified grant id, so the hub can
bind a session identity to the credential that opened the socket. The version
and the envelope ship together, so the hub and the Worker must be redeployed
together. A hub that reaches an older Worker closes the socket and reports
**The relay is outdated; redeploy the Worker**; the hub also drops any unwrapped
client frame. Remote access is unavailable between the two deploys; pairing
payloads and the local listener are unaffected.

The Worker's `GET /health` answers `{ ok, protocol, relay }`, where `relay` is
the route-envelope version (currently `3`). The panel's deployment check
refuses a Worker that omits `relay` or reports a version below what the hub
speaks, so an outdated deployment fails at deploy time with the same message
instead of at the first upgrade.

## Deployment

### From the hub panel

A hub build compiled with `ENABLE_CLOUDFLARE_DEPLOYMENT=true` can deploy the relay
from the panel. The panel asks for a Cloudflare API token scoped to
**Workers Scripts: Edit**, **Zone: Read**, and **Zone: Workers Routes: Edit**.
**Account Settings: Read** is optional and only lets the panel list accounts;
without it, enter the account ID manually. A `403` from any call names those
scopes. The hub calls the Cloudflare REST API directly; it does not run Wrangler
or store the token in `server.json`.

The deployment:

1. lists the token's accounts and reads the account's `workers.dev` subdomain;
2. uploads `dist/relay/worker.mjs` with the `RELAY_ROOMS` Durable Object binding,
   a first-deploy `new_sqlite_classes` migration, and `CLARA_AGENT_TOKEN` as a
   `secret_text` binding;
3. enables the Worker on `workers.dev` and waits for `GET /health` to report a
   compatible `relay` version (see [Relay version](#relay-version));
4. when the panel submits a custom hostname, reads the account's zones with
   `GET /zones?account.id=<account>&per_page=50`, lists the script's existing
   bindings with `GET /accounts/<account>/workers/domains?service=<script>`, and
   attaches the hostname with `PUT /accounts/<account>/workers/domains` and the
   body `{ zone_id, hostname, service, environment: "production" }`. A matching
   hostname in the same zone reuses its binding, so a redeploy does not create a
   duplicate; a hostname bound in another zone is detached first;
5. polls the custom hostname's `GET /health` for up to five minutes with capped
   backoff. Cloudflare provisions DNS and the certificate asynchronously, so this
   window is longer than the `workers.dev` check. When the relay version is
   compatible, the deployed URL becomes `wss://<hostname>` and the record stores
   `customDomain: { hostname, zoneId, domainId, ready: true }`. If the window
   expires, the deployment keeps the `workers.dev` URL, records `ready: false`,
   and returns a warning instead of failing;
6. only after the custom host answers, an opt-in `disableWorkersDev` posts
   `{ enabled: false, previews_enabled: false }` to the script subdomain endpoint
   and the deployed URL stays on the custom hostname. Without a custom hostname
   that switch is never applied, and a failed disable becomes a warning;
7. writes the relay URL and room to `server.json`, stores the hub token
   encrypted in `relay-credentials.json`, and applies the relay without a hub
   restart; a legacy plaintext token in `server.json` is moved into that sealed
   file on the next startup;
8. optionally stores the Cloudflare token encrypted in `cloudflare-api-token.json`.

Forgetting the deployment, or a panel relay edit that invalidates it, detaches
the stored binding with `DELETE /accounts/<account>/workers/domains/<domainId>`.
Deploying a different hostname attaches the new binding first and then detaches
the old one; a binding that is already gone is treated as detached. Deleting the
Worker in Cloudflare still removes its domains, so the panel record is the
source for the detach call.

Preview and version URLs are off by default. `infra/relay/wrangler.jsonc` sets
`preview_urls: false`, and the panel deploy sends `previews_enabled: false` on the
Worker subdomain settings on every deploy, so redeploying clears URLs an earlier
deploy enabled. Turning them on is an explicit opt-in because each version gets
an extra `workers.dev` hostname outside host-scoped WAF and rate-limit rules. To
confirm the setting against a real Cloudflare account, follow
[relay preview URL verification](../features/relay-preview-verification.md).

Every existing device and adapter must pair again to receive an enrollment grant
under v4. The deployment is blocked while any relay environment variable is set,
because those values would override the deployed target. The feature is compile-time optional;
the panel UI, routes, API code, and worker artifact are absent from a build
without the flag. The manual Wrangler path below remains the supported fallback.

### Manually

1. Create the Pages project and custom domain; build with
   `pnpm --filter @clara/web build` and output `apps/web/dist`.
2. Set `VITE_CLARA_WS_URL=wss://relay.example` in the Pages build environment,
   using your own relay host. This is optional: leave it unset to follow each
   pairing payload's own relay URL and room.
3. Deploy the Worker with `pnpm deploy:relay`; it creates the DO namespace. Add
   your own custom domain route in `infra/relay/wrangler.jsonc` or the
   Cloudflare dashboard, or use the workers.dev URL.
4. Set the Worker secret, then open the hub panel's **Relay** card and save the
   Worker URL (`wss://…`) with the same hub token. The hub stores the token
   encrypted in `relay-credentials.json`; the URL and generated room stay in
   `server.json`. Set **Web URL** to your web URL as well.
5. Environment variables remain available for CI and headless bootstrap:
   `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`, and `CLARA_AGENT_TOKEN`. Each one wins
   over the matching panel value when set; the panel is the fallback. Values
   supplied by the environment are never written to disk.
6. The room is always generated by the hub. When no room exists it generates one
   and persists it in `server.json`; keep that value stable because every pairing
   code is scoped to it. The panel can replace it with another random value, but
   cannot set free text.
7. Run `node apps/hub/server/dist/index.js pair` and scan the QR from the phone.

## Failure behavior

| Failure                   | Result                                                                                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Relay unreachable         | Hub retries with exponential backoff (1s–30s, jittered).                                                                                                                       |
| Hub offline               | Clients connect, then close with `1013`; the connect screen shows failure.                                                                                                     |
| Hub restarts              | DO closes clients with `1012`; both sides re-handshake.                                                                                                                        |
| Adapter offline           | Hub returns `harness_offline`; the adapter reconnects with backoff.                                                                                                            |
| Wrong hub token or grant  | Worker returns `401` before upgrading.                                                                                                                                         |
| Another hub took the room | The old hub socket closes with `4002`; the hub records a replacement warning and waits at least 30s to reconnect.                                                              |
| Outdated relay            | Hub reports **The relay is outdated; redeploy the Worker** and stays offline until the Worker is updated.                                                                      |
| Unknown or revoked device | Hub sends an `error` frame; a transient code reconnects, a credential-dead code stops after three in a row.                                                                    |
| Room full                 | The DO refuses the 33rd client socket, or a 9th from one address, with `4008` and a reason naming the limit.                                                                   |
| Per-peer rate limited     | A browser above 60 frames/s or 512 KiB/s, or an adapter above 600 frames/s or 4 MiB/s, closes with `4008`; no later frame is forwarded and the client reconnects with backoff. |
| Oversized client frame    | A frame above 128 KiB closes with `4009`; no later frame is forwarded.                                                                                                         |
| Hub session limit         | A hello beyond 64 live sessions gets `not_allowed`; the client retries with backoff.                                                                                           |
| Version mismatch          | Handshake is rejected; update web and hub together.                                                                                                                            |
| Slow client               | DO closes above the buffered-output threshold.                                                                                                                                 |
| Many clients              | Egress scales with client count because hub frames are broadcast.                                                                                                              |
