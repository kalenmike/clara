# Relay

The relay lets a browser or installed PWA reach a Clara home agent that is not
publicly reachable. The agent opens one outbound WebSocket to Cloudflare; the
browser opens one inbound WebSocket to the same room. Cloudflare only forwards
opaque frames.

```text
OpenCode HTTP/SSE
      ▲
      │ basic auth (server-side)
      ▼
Clara home agent ──outbound WSS──▶ Worker ──▶ RelayRoom DO ◀──WSS── browser / PWA
      │                                              │
      └──────────── E2EE payloads ───────────────────┘
```

## Components

| Component       | Location                | Responsibility                                                |
| --------------- | ----------------------- | ------------------------------------------------------------- |
| Home agent      | `apps/server`           | OpenCode auth, HTTP/SSE proxy, E2EE sessions, relay reconnect |
| Relay Worker    | `workers/relay`         | Path routing, subprotocol/token auth, static health endpoint  |
| `RelayRoom` DO  | `workers/relay`         | One agent socket + N client sockets; frame forwarding only    |
| Web transport   | `apps/web`              | Fetch-over-WebSocket shim, E2EE, reconnect, heartbeat         |
| Shared protocol | `packages/shared-types` | Frame/action/state types and pairing payloads                 |
| Crypto          | `packages/crypto`       | PSK derivation, AES-GCM seal/open, replay guard               |

## Domain layout

| Host                           | Service                                   |
| ------------------------------ | ----------------------------------------- |
| `clara.kalenmichael.com`       | Cloudflare Pages project `clara`          |
| `relay.clara.kalenmichael.com` | Worker `clara-relay`, custom domain route |

The Worker route is `/room/:roomId`. The room id is a 128-bit base64url value
generated by the home agent and stored in `~/.config/clara/server.json`. It is
not a secret, but it is unguessable.

## Room behavior

- A room has exactly one agent socket. A new agent connection closes the old
  one with code `4002` and closes clients with `1012` so they re-handshake
  against the new process.
- Client frames go only to the agent. Agent frames are broadcast to every
  client. There is no per-client routing state in the DO.
- Each client uses its own `sid` and per-session keys. Foreign frames fail to
  decrypt and are dropped; the relay does not need to understand them.
- When the agent disconnects, clients close with `1012` and reconnect with
  jittered backoff.
- When no agent is present, a client frame closes that client with `1013`.
- No message backlog, storage, alarms, or CRDT state. A mobile client that
  resumes after a gap reconnects and invalidates its cached queries.
- The DO uses WebSocket hibernation and has no Durable Object storage bindings.

## Authentication

Browsers cannot send an `Authorization` header on a WebSocket, so auth travels
in `Sec-WebSocket-Protocol`:

```text
clara.v1
clara.role.client | clara.role.agent
clara.auth.<token>
```

The Worker checks the role-specific token with a constant-time comparison, then
forwards a trusted `x-clara-role` header to the DO. Use separate secrets:

```bash
cd workers/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
pnpm exec wrangler secret put CLARA_CLIENT_TOKEN
```

The client token is embedded in the pairing payload. It prevents unpaired
traffic from reaching the agent, but it is not the encryption key. An attacker
with the client token and no PSK can open sockets and cause noise; they cannot
read or forge E2EE frames. Rotate both tokens if either leaks.

## Deployment

1. Create the Pages project and custom domain; build with
   `pnpm --filter @clara/web build` and output `apps/web/dist`.
2. Set `VITE_CLARA_WS_URL=wss://relay.clara.kalenmichael.com` in the Pages build
   environment.
3. Deploy the Worker with `pnpm deploy:relay`; it creates the DO namespace and
   binds the custom domain.
4. Set the Worker secrets and matching server environment variables.
5. Start the home agent with `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`,
   `CLARA_AGENT_TOKEN`, and `CLARA_CLIENT_TOKEN`.
6. Run `node apps/server/dist/index.js pair` and scan the QR from the phone.

## Failure behavior

| Failure                 | Result                                                                     |
| ----------------------- | -------------------------------------------------------------------------- |
| Relay unreachable       | Agent retries with exponential backoff (1s–30s, jittered).                 |
| Agent offline           | Clients connect, then close with `1013`; the connect screen shows failure. |
| Agent restarts          | DO closes clients with `1012`; both sides re-handshake.                    |
| Wrong token             | Worker returns `401` before upgrading.                                     |
| Wrong PSK / fingerprint | Transport closes with `4001`; UI reports a key mismatch.                   |
| Version mismatch        | Handshake is rejected; update web and agent together.                      |
| Slow client             | DO closes above the buffered-output threshold.                             |
| Many clients            | Egress scales with client count because agent frames are broadcast.        |
