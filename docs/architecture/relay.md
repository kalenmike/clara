# Relay

The relay lets a browser, installed PWA, or harness adapter reach a Clara hub
that is not publicly reachable. The hub opens one outbound WebSocket to
Cloudflare; browsers and adapters open inbound WebSockets to the same room.
Cloudflare only forwards opaque frames.

```text
Harness ──HTTP/SSE──▶ adapter ──outbound WSS──▶ Worker ──▶ RelayRoom DO ◀──outbound WSS── hub
                                                                    ▲
                                                                    └──WSS── browser / PWA
```

In local mode an adapter opens the hub's local WebSocket directly instead of
joining the relay room.

## Components

| Component       | Location                          | Responsibility                                                 |
| --------------- | --------------------------------- | -------------------------------------------------------------- |
| Hub service     | `apps/hub/server`                 | Hub `/v1` API, adapter routing, E2EE sessions, relay reconnect |
| Adapter         | `apps/adapters/*`                 | Harness translation, harness auth, adapter E2EE and reconnect  |
| Relay Worker    | `infra/relay`                     | Path routing, subprotocol/token auth, static health endpoint   |
| `RelayRoom` DO  | `infra/relay`                     | One hub socket + N client sockets; frame forwarding only       |
| Web transport   | `apps/web`                        | Fetch-over-WebSocket shim, E2EE, reconnect, heartbeat          |
| Shared protocol | `packages/contracts/shared-types` | Frame/action/state types and pairing payloads                  |
| Crypto          | `packages/crypto`                 | device-key derivation, AES-GCM seal/open, replay guard         |

## Example domain layout

| Host            | Service                                  |
| --------------- | ---------------------------------------- |
| `clara.example` | Cloudflare Pages project for the web app |
| `relay.example` | Worker custom domain route for the relay |

The Worker route is `/room/:roomId`. The room id is a 128-bit base64url value
generated by the hub and stored in `~/.config/clara/server.json`. It is
not a secret, but it is unguessable. The panel never accepts a room as text; it
only regenerates a fresh random value.

## Room behavior

- A room has exactly one hub socket. A new hub connection closes the old
  one with code `4002` and closes clients with `1012` so they re-handshake
  against the new process.
- Browsers and adapters are both clients of the room. Client frames go only to
  the hub. Hub frames are broadcast to every client. There is no per-client
  routing state in the DO.
- Each client uses its own `sid` and per-session keys. The hello also carries a
  stable `deviceId` for a browser or a stable adapter identity for an adapter, so
  the relay can correlate connections from one peer even though the `sid` is
  fresh. Foreign frames fail to decrypt and are dropped; the relay does not need
  to understand them.
- When the hub disconnects, clients close with `1012` and reconnect with
  jittered backoff.
- When no hub is present, a client frame closes that client with `1013`.
- No message backlog, storage, alarms, or CRDT state. A mobile client that
  resumes after a gap reconnects and invalidates its cached queries.
- The DO uses WebSocket hibernation and has no Durable Object storage bindings.

## Authentication

Browsers cannot send an `Authorization` header on a WebSocket, so auth travels
in `Sec-WebSocket-Protocol`:

```text
clara.v1
clara.role.client | clara.role.agent
clara.auth.<token>
```

The Worker checks the role-specific token with a constant-time comparison, then
forwards a trusted `x-clara-role` header to the DO. Use separate secrets:

```bash
cd infra/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
pnpm exec wrangler secret put CLARA_CLIENT_TOKEN
```

The client token is embedded in the pairing payload for browsers and adapters. It
prevents unpaired traffic from reaching the hub, but it is not the encryption
key. An attacker with the client token and no device or adapter key can open
sockets and cause noise; they cannot read or forge E2EE frames. Rotate both
tokens if either leaks. Adapter pairing also issues its own adapter credential;
that credential authenticates the adapter after enrollment.

The hub's relay role and secret keep the historical `agent` name
(`clara.role.agent`, `CLARA_AGENT_TOKEN`), while prose calls that side the hub.

## Deployment

### From the hub panel

A hub build compiled with `ENABLE_CLOUDFLARE_DEPLOYMENT=true` can deploy the relay
from the panel. The panel asks for a Cloudflare API token scoped to
**Workers Scripts: Edit** and, for account discovery, **Account Settings: Read**.
The hub calls the Cloudflare REST API directly; it does not run Wrangler or store
the token in `server.json`.

The deployment:

1. lists the token's accounts and reads the account's `workers.dev` subdomain;
2. uploads `dist/relay/worker.mjs` with the `RELAY_ROOMS` Durable Object binding,
   a first-deploy `new_sqlite_classes` migration, and both relay tokens as
   `secret_text` bindings;
3. enables the Worker on `workers.dev` and waits for `GET /health`;
4. writes the relay URL and room to `server.json`, stores both tokens encrypted
   in `relay-credentials.json`, and applies the relay without a hub restart;
   legacy plaintext tokens in `server.json` are moved into that sealed file on
   the next startup;
5. optionally stores the Cloudflare token encrypted in `cloudflare-api-token.json`.

Existing devices keep their old pairing endpoint and must pair again. The
deployment is blocked while any relay environment variable is set, because those
values would override the deployed target. The feature is compile-time optional;
the panel UI, routes, API code, and worker artifact are absent from a build
without the flag. The manual Wrangler path below remains the supported fallback.

### Manually

1. Create the Pages project and custom domain; build with
   `pnpm --filter @clara/web build` and output `apps/web/dist`.
2. Set `VITE_CLARA_WS_URL=wss://relay.example` in the Pages build environment,
   using your own relay host. This is optional: leave it unset to follow each
   pairing payload's own relay URL and room.
3. Deploy the Worker with `pnpm deploy:relay`; it creates the DO namespace. Add
   your own custom domain route in `infra/relay/wrangler.jsonc` or the
   Cloudflare dashboard, or use the workers.dev URL.
4. Set the Worker secrets, then open the hub panel's **Relay** card and save the
   Worker URL (`wss://…`) with the same hub and client tokens. The hub stores the
   tokens encrypted in `relay-credentials.json`; the URL and generated room stay
   in `server.json`. Set **Web URL** to your web URL as well.
5. Environment variables remain available for CI and headless bootstrap:
   `CLARA_RELAY_URL`, `CLARA_RELAY_ROOM`, `CLARA_AGENT_TOKEN`, and
   `CLARA_CLIENT_TOKEN`. Each one wins over the matching panel value when set;
   the panel is the fallback. Values supplied by the environment are never
   written to disk.
6. The room is always generated by the hub. When no room exists it generates one
   and persists it in `server.json`; keep that value stable because every pairing
   code is scoped to it. The panel can replace it with another random value, but
   cannot set free text.
7. Run `node apps/hub/server/dist/index.js pair` and scan the QR from the phone.

## Failure behavior

| Failure                   | Result                                                                     |
| ------------------------- | -------------------------------------------------------------------------- |
| Relay unreachable         | Hub retries with exponential backoff (1s–30s, jittered).                   |
| Hub offline               | Clients connect, then close with `1013`; the connect screen shows failure. |
| Hub restarts              | DO closes clients with `1012`; both sides re-handshake.                    |
| Adapter offline           | Hub returns `harness_offline`; the adapter reconnects with backoff.        |
| Wrong token               | Worker returns `401` before upgrading.                                     |
| Unknown or revoked device | Hub sends an `error` frame; the client reports and stops reconnecting.     |
| Version mismatch          | Handshake is rejected; update web and hub together.                        |
| Slow client               | DO closes above the buffered-output threshold.                             |
| Many clients              | Egress scales with client count because hub frames are broadcast.          |
