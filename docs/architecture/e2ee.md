# End-to-end encryption

Clara encrypts every WebSocket payload between the browser transport and the
hub. Cloudflare, the relay Worker, and the Durable Object see ciphertext,
frame sizes, timing, room ids, and connection metadata. They never see OpenCode
requests, responses, prompts, or the OpenCode password.

## Key model

- Each paired device has its own 256-bit symmetric key. There is no shared
  browser key.
- The browser generates the key during enrollment and stores it as a
  **non-extractable** `CryptoKey` in IndexedDB. Raw key bytes are not written to
  `localStorage`.
- The hub stores each device key encrypted at rest with
  `~/.config/clara/secrets.key` (mode `0600`).
- A pairing link carries a one-time enrollment token, never a long-lived key.
  The token is valid for 10 minutes, is consumed by one device, and is stored
  encrypted on the hub until it is used or expires.
- The relay client token is still shared by every device. It gates relay socket
  access but is not the encryption key.
- The device fingerprint is a truncated SHA-256 of the device key. It is shown
  in the panel and can be compared after enrollment.

## Handshake

```text
client ── hello { sid, deviceId | enrollId, nonceC } ──▶ hub
hub    ── hello { sid, nonceS } ──▶ broadcast
hub    ── sealed ready { agentInfo } ──▶ broadcast
client ── sealed ready.ack ──▶ hub
```

- `sid` is a random 128-bit connection id generated per connection.
- `deviceId` is a random 128-bit logical device id generated by the browser
  during enrollment. It is stable across reconnects and visible to the relay.
- `enrollId` is a public enrollment id. The one-time token is the key for the
  enrollment session only.
- Keys are derived with HKDF-SHA-256 from the device key (or enrollment token),
  a salt over `sid | nonceC | nonceS`, and directional info strings
  `clara/v2/c2s` and `clara/v2/s2c`.
- A fresh client nonce per connection prevents replaying an old handshake.
- A replayed or out-of-order frame is rejected by a strict sequence guard before
  decryption.

## Enrollment

```text
pair command
  -> creates a pairing_tokens row { id, expiresAt, encrypted token }
  -> prints a link with enrollId, enrollToken, fingerprint, and expiry

client
  -> hello { enrollId }
hub
  -> derives the enrollment session from the one-time token
client
  -> device.enroll { deviceId, key, label }
hub
  -> stores the device and encrypted key
  -> marks the token used
  -> device.enrolled { deviceId, fingerprint, label }
client
  -> stores the non-extractable key in IndexedDB
  -> reconnects with hello { deviceId }
```

The enrollment session ends after `device.enrolled` is sent. The hub retires
it immediately instead of waiting for the idle sweep, so the panel never shows
a completed pairing as a device-less client. A pairing still in flight is marked
as such.

The device id is generated by the browser so a lost enrollment response can be
retried with the same identity. The hub rejects a second device that reuses a
consumed token.

## Envelope

Every sealed frame is JSON with a small plaintext header so clients can filter
broadcast frames:

```json
{ "t": "sealed", "v": 2, "sid": "…", "seq": 0, "iv": "…", "ct": "…" }
```

- AES-256-GCM with a random 12-byte nonce per frame.
- AAD binds `sid`, direction, and sequence number.
- `ct` and `iv` are base64url.
- Payload chunks are capped at 32 KiB before encryption, keeping frames under
  the Workers WebSocket message limit.

## Actions and states

`packages/contracts/shared-types` defines the payload unions:

- Actions (browser → hub): `http.request`, `http.abort`, `ping`, `pong`,
  `ready`, `ready.ack`, `device.enroll`, `push.subscribe`, `push.unsubscribe`,
  `push.test`, `sync.check`, `sync.pull`, `sync.push`.
- States (hub → browser): `http.response`, `http.chunk`, `http.end`,
  `http.error`, `agent.status`, `push.status`, `sync.revision`,
  `sync.snapshot`, `sync.error`, `device.enrolled`.
- `agent.status` also carries the current hub info when an admin changes the
  client-sync gate or cadence, so connected clients update without reconnecting.

The hub routes `/v1` requests through the hub API. The API strips hop-by-hop
headers, adds OpenCode basic auth, and prevents origin changes. The browser
never receives the OpenCode password in relay mode.

Push subscription management is sealed like every other action. Push delivery
itself leaves the E2EE channel: `web-push` encrypts the payload to the browser's
subscription keys and posts it to the browser vendor's push endpoint. The push
service cannot read the payload, but it sees the endpoint and delivery metadata.

## Threat model

| Threat                                | Mitigation                                                   |
| ------------------------------------- | ------------------------------------------------------------ |
| Cloudflare reads traffic              | AES-GCM payloads; no plaintext request data                  |
| Relay token leak                      | Attacker can open sockets but cannot decrypt without a key   |
| Captured frame replayed               | Per-session monotonic sequence + fresh handshake nonces      |
| Tampered ciphertext                   | GCM authentication tag and AAD                               |
| Stolen browser storage                | Non-extractable device key; revoke one device                |
| Stolen pairing link                   | One-time 10-minute token; one device; no long-lived key      |
| Lost device                           | Revoke it in the panel; other devices keep working           |
| Relay sees device correlation         | Stable `deviceId` in the plaintext hello; accepted trade-off |
| XSS in the Pages origin               | CSP, no third-party scripts; a key is usable while open      |
| Malicious client impersonates the hub | Device keys would not match; sealed frames fail to decrypt   |

## Revocation

- The panel revokes one device, deletes its encrypted key, aborts its live
  sessions, and removes its push subscriptions.
- A revoked device cannot complete a new handshake.
- A revoked record can be deleted permanently from the panel. The key is already
  gone, so the device is rejected as unknown instead of revoked.
- Revoking one device never rotates another device or the hub.

## Limitations

- No forward secrecy in v2; the per-device key protects that device's sessions.
- No hardware binding. A copied browser profile may still use a non-extractable
  key depending on the browser.
- XSS on the origin can act as the device while the page is open; it cannot
  export the raw key.
- The relay client token is shared by every paired device.
- The relay sees a stable device id and can correlate a device's connections.
- A stolen enrollment link can enroll one device before it expires; the panel
  shows the device and can revoke it immediately.
