# Remote access with the relay

A browser or adapter on another network cannot reach a hub that only listens on
`127.0.0.1`. The relay solves that by having the hub open one outbound WebSocket
to Cloudflare and letting browsers and harness adapters join the same room.
Cloudflare forwards encrypted frames; it cannot read them.

## What you need

- A Cloudflare account.
- A domain for the relay, or the generated `workers.dev` URL.
- A web deployment served over HTTPS, either Cloudflare Pages or the web
  container behind TLS.

## Deploy the Worker

### From the hub panel

If your Clara build includes the optional Cloudflare deployment feature, open
**Connections → Relay → Deploy relay to Cloudflare** in the hub panel.

1. Create a Cloudflare API token from the link in the panel. It needs
   **Workers Scripts: Edit**, **Zone: Read**, and **Zone: Workers Routes: Edit**.
   **Account Settings: Read** lets the panel list your accounts; without it, you
   can type the account ID.
2. Paste the token, choose the account, and choose **Deploy relay**.
3. Clara uploads the Worker, creates its Durable Object namespace, sets the hub
   token, enables the `workers.dev` host, and health-checks it.

To serve the relay on your own host, enter a **Custom domain** before deploying.
Choose **Load zones**, pick the zone that holds the name, and enter a bare
hostname such as `relay.example.com` with no scheme, path, or wildcard. Clara
attaches the hostname to the Worker and waits up to five minutes for Cloudflare
to issue the certificate and for the relay to answer there. If the host does not
answer in time, the deployment stays on `workers.dev` and the panel shows a
warning; deploy again once the certificate is ready. A successful custom domain
becomes the relay URL in the panel, so existing devices must pair again.

Under **Advanced**, **Disable the workers.dev hostname** turns the fallback host
off after the custom host answers. Only use it when you want the custom hostname
to be the only relay URL. The panel never turns `workers.dev` off when no custom
hostname is set, or before the custom host passes its health check.

Preview and version URLs are off by default. Each version would get its own
extra `workers.dev` hostname, and those hostnames bypass WAF and rate-limit rules
scoped to the relay host. Turn them on only when you need to test a version
directly: the panel keeps them off on every deploy unless you opt in under
**Advanced**.

The hub stores the relay hub token encrypted on this machine. The Cloudflare
token is kept only for the deployment unless you choose to save it. Existing
devices must pair again after the relay changes. A relay URL, room, or token
supplied by the environment takes precedence, so remove those variables before
deploying a relay from the panel.

Builds without the feature use the manual path below.

### Confirm preview and version URLs are off

After a panel deploy, open **Workers & Pages → `<Worker>` → Settings → Domains &
Routes** and check **Version URLs**; Cloudflare still calls the setting preview
URLs in some places. It should be disabled. The **Deployments** tab shows a
version URL for a non-production version only when the setting is on, so no
extra hostname there confirms the same thing. The ordinary `workers.dev` host
keeps answering: `https://<worker>.<subdomain>.workers.dev/health` returns
`{"ok":true}`.

If you turned the setting on under **Advanced**, turn it off and deploy again.
Clara applies the disabled setting on every deploy, so the extra hostnames go
away without deleting the Worker. Cloudflare does not generate version URLs for
Workers that use a Durable Object, which the relay does, so an opt-in test may
show no extra hostname even when Cloudflare accepts the setting.

### Manually

The Worker and its `RelayRoom` Durable Object live in `infra/relay`.

```bash
cd infra/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
pnpm exec wrangler deploy
```

From the repository root, the same deploy is `pnpm deploy:relay`.

Use one random value. The hub token must be 32 to 512 characters with no spaces
or commas; the panel refuses to save one that breaks the rule. The Worker uses it
for the hub's agent role and to sign per-device relay grants. Rotate it if it
leaks, then redeploy the Worker and pair every device again.

If the hub panel reports that the relay is outdated, redeploy the Worker with
`pnpm deploy:relay`, or use **Deploy relay** in the panel. The hub and the Worker
must run the same relay version; until both are updated, remote access stays
offline.

The default configuration uses the `workers.dev` URL. For a custom host, add a
route in `infra/relay/wrangler.jsonc`:

```jsonc
"routes": [{ "pattern": "relay.example.com", "custom_domain": true }]
```

The Worker serves `/room/:roomId`. The room id is generated by the hub and is not
a secret, but it is unguessable.

A room holds up to 32 browser and adapter connections, with at most eight from
one network address. Each connection may send 60 frames or 512 KiB per second,
and a single frame is limited to 128 KiB. These limits apply to the relay only;
a local connection is not capped this way.

## Point the web client at the relay

`VITE_CLARA_WS_URL` is optional. Each pairing payload carries its hub's relay URL
and room, so a web build can connect to any relay when this value is left empty.
This is the right choice for a shared hosted web client.

Set it only when the browser must use one fixed relay endpoint regardless of the
pairing payload:

```bash
VITE_CLARA_WS_URL=wss://relay.example pnpm --filter @clara/web build
```

For the web container, put the same value in `infra/docker/.env` and rebuild with
`--build`. The value is baked into the web build.

## Configure the hub

Open **Connections → Relay** in the hub panel and save the relay URL with the
same hub token you set on the Worker. The hub generates a random room
automatically and connects without a restart. The token is encrypted on this
machine and is never shown again. Changing the room or hub token later requires
every device to pair again.

The room is always generated. You can replace it with **Regenerate room**, but
you cannot type a room name.

A relay URL saved without the hub token does not block the hub. It starts
local-only, the Relay card marks the missing token, and saving it connects the
relay without a restart.

Environment variables are the fallback for CI or headless bootstrap:

```bash
CLARA_RELAY_URL=wss://relay.example \
CLARA_AGENT_TOKEN=... \
pnpm clara start hub --local
```

Each variable wins over the matching panel value when it is set. Values supplied
by the environment are not written to disk, so removing the variable later
restores the panel value. `CLARA_RELAY_ROOM` is optional; when it and the panel
room are both absent, the hub generates one and persists it in `server.json`.
Keep that value stable: every pairing code is scoped to it.

Confirm the relay card is connected, and set **Web URL** to the public HTTPS URL.
`CLARA_PAIRING_BASE_URL` overrides the panel value. When an adapter must reach the
hub from another network, choose **Remote** for it in
**Harness → Pair Harness**.

## If another hub takes the room

A room accepts one hub connection. If the Relay card repeatedly says **Another
hub connected to this room**, a second hub process is using the same hub token
and room, or the token has leaked. Fix it before devices start dropping:

1. Find and stop the other hub process. Look on other machines, in old
   containers, and in a copy started with a different config directory. Only one
   hub should serve this room.
2. Rotate the Worker secret and save the same value in **Connections → Relay**:

   ```bash
   cd infra/relay
   pnpm exec wrangler secret put CLARA_AGENT_TOKEN
   ```

   Saving the Relay card applies the new token without a hub restart. Deploying
   the relay from the panel also writes it.

3. Confirm the Relay card stays connected and the warning does not return.
4. If the Cloudflare API token may have leaked, rotate it in Cloudflare and
   update the deployment token in the panel.

Rotating the hub token does not require devices to pair again. Pair again only
when the relay URL or the room changes.

## Upgrading to v4

Handshake v4 replaces the shared relay client token with per-device signed
grants. Update the relay Worker, hub, web client, and adapters together, and
remove `CLARA_CLIENT_TOKEN` if it is still set. Each device and adapter pairs
once more: the pairing link carries a ten-minute enrollment grant, and the
device then receives a thirty-day grant that the hub refreshes on every connect.

## Pair a remote device

Open **Clients → Pair Client** in the hub panel and scan the QR or open the
link on the phone. You can also run:

```bash
pnpm clara pair
```

A relay code uses the public Web URL and the `wss://` endpoint. Choose **Local
connection only** in the panel, or use `--no-relay`, to keep a direct `ws://`
address that only works on the same machine or network.

## Failure behavior

| Failure               | Result                                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| Relay unreachable     | The hub retries with backoff and the panel shows the relay state.                                           |
| Hub token missing     | The hub starts local-only; save the hub token in **Connections → Relay**.                                   |
| Relay outdated        | The hub reports that the relay must be redeployed and stays offline until both sides run the same version.  |
| Hub offline           | Clients connect to the room, then close and report a connection failure.                                    |
| Hub restart           | Clients close and re-handshake with their stored device key.                                                |
| Wrong token or grant  | The Worker rejects the upgrade with `401`.                                                                  |
| Another hub connected | The Relay card reports another hub in the room; stop the second hub and rotate the hub token.               |
| Room full             | The room already has 32 connections, or eight from this address; close an unused device or reconnect later. |
| Rate limited          | A connection that sends too many frames or bytes is disconnected and reconnects with backoff.               |
| Hub at capacity       | The hub is already serving its maximum relay sessions; the client retries shortly.                          |
| Revoked device        | The hub rejects the device; the client stops reconnecting once the rejection repeats.                       |
| Version mismatch      | Update the web client and hub together.                                                                     |

## Security notes

- The relay sees ciphertext, frame sizes, timing, room ids, and connection
  metadata. It does not see prompts or replies.
- Relay access uses a signed grant per device or adapter, not a shared client
  token. A grant is not the encryption key, and the relay binds each session to
  the connection that opened it. A leaked grant can open sockets and add traffic
  within the room limits until it expires, but it cannot read or act without the
  device key. Grants last thirty days and are refreshed on each connect.
- The hub panel is loopback-only. Use an SSH tunnel if you need to reach it
  remotely; do not expose it to the internet.
- Enter the Cloudflare API token only in the hub panel over loopback or HTTPS.
  The hub uses it for the deployment and never returns it to the browser. Saving
  it is optional and encrypted with the hub secret key.
- Use HTTPS for the web app. An HTTPS page cannot open a `ws://` socket.
