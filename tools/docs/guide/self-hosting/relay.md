# Remote access with the relay

A browser or adapter on another network cannot reach a hub that only listens on
`127.0.0.1`. The relay solves that by having the hub open one outbound WebSocket
to Cloudflare and letting browsers and harness adapters join the same room.
Cloudflare forwards encrypted frames; it cannot read them.

## What you need

- A Cloudflare account.
- A domain for the relay, or the generated `workers.dev` URL.
- A web deployment served over HTTPS, either Cloudflare Pages or the web
  container behind TLS.

## Deploy the Worker

### From the hub panel

If your Clara build includes the optional Cloudflare deployment feature, open
**Connections → Relay → Deploy relay to Cloudflare** in the hub panel.

1. Create a Cloudflare API token from the link in the panel. It needs
   **Workers Scripts: Edit**; **Account Settings: Read** lets the panel list your
   accounts.
2. Paste the token, choose the account, and choose **Deploy relay**.
3. Clara uploads the Worker, creates its Durable Object namespace, sets both
   relay tokens, enables the `workers.dev` host, and health-checks it.

Preview and version URLs are off by default. Each version would get its own
extra `workers.dev` hostname, and those hostnames bypass WAF and rate-limit rules
scoped to the relay host. Turn them on only when you need to test a version
directly: the panel keeps them off on every deploy unless you opt in under
**Advanced**.

The hub stores the relay tokens encrypted on this machine. The Cloudflare token
is kept only for the deployment unless you choose to save it. Existing devices
must pair again after the relay changes. A relay URL, room, or token supplied by
the environment takes precedence, so remove those variables before deploying a
relay from the panel.

Builds without the feature, and custom-domain deployments, use the manual path
below.

### Manually

The Worker and its `RelayRoom` Durable Object live in `infra/relay`.

```bash
cd infra/relay
pnpm exec wrangler secret put CLARA_AGENT_TOKEN
pnpm exec wrangler secret put CLARA_CLIENT_TOKEN
pnpm exec wrangler deploy
```

From the repository root, the same deploy is `pnpm deploy:relay`.

Use two different, random values. The hub uses the agent token; pairing payloads
for browsers and adapters embed the client token. Rotate both if either leaks.

The default configuration uses the `workers.dev` URL. For a custom host, add a
route in `infra/relay/wrangler.jsonc`:

```jsonc
"routes": [{ "pattern": "relay.example.com", "custom_domain": true }]
```

The Worker serves `/room/:roomId`. The room id is generated by the hub and is not
a secret, but it is unguessable.

## Point the web client at the relay

`VITE_CLARA_WS_URL` is optional. Each pairing payload carries its hub's relay URL
and room, so a web build can connect to any relay when this value is left empty.
This is the right choice for a shared hosted web client.

Set it only when the browser must use one fixed relay endpoint regardless of the
pairing payload:

```bash
VITE_CLARA_WS_URL=wss://relay.example pnpm --filter @clara/web build
```

For the web container, put the same value in `infra/docker/.env` and rebuild with
`--build`. The value is baked into the web build.

## Configure the hub

Open **Connections → Relay** in the hub panel and save the relay URL with the
same hub and client tokens you set on the Worker. The hub generates a random room
automatically and connects without a restart. Tokens are encrypted on this
machine and are never shown again. Changing the room or client token later
requires every device to pair again.

The room is always generated. You can replace it with **Regenerate room**, but
you cannot type a room name.

A relay URL saved without both tokens does not block the hub. It starts
local-only, the Relay card marks the missing tokens, and saving them connects
the relay without a restart.

Environment variables are the fallback for CI or headless bootstrap:

```bash
CLARA_RELAY_URL=wss://relay.example \
CLARA_AGENT_TOKEN=... \
CLARA_CLIENT_TOKEN=... \
pnpm clara server start --local
```

Each variable wins over the matching panel value when it is set. Values supplied
by the environment are not written to disk, so removing the variable later
restores the panel value. `CLARA_RELAY_ROOM` is optional; when it and the panel
room are both absent, the hub generates one and persists it in `server.json`.
Keep that value stable: every pairing code is scoped to it.

Confirm the relay card is connected, and set **Web URL** to the public HTTPS URL.
`CLARA_PAIRING_BASE_URL` overrides the panel value. When an adapter must reach the
hub from another network, choose **Cloudflare relay** as its location in
**Harness → Add harness**.

## Pair a remote device

Open **Clients → Pair a browser** in the hub panel and scan the QR or open the
link on the phone. You can also run:

```bash
pnpm clara pair
```

A relay code uses the public Web URL and the `wss://` endpoint. Choose **Local
connection only** in the panel, or use `--no-relay`, to keep a direct `ws://`
address that only works on the same machine or network.

## Failure behavior

| Failure              | Result                                                                   |
| -------------------- | ------------------------------------------------------------------------ |
| Relay unreachable    | The hub retries with backoff and the panel shows the relay state.        |
| Relay tokens missing | The hub starts local-only; save both tokens in **Connections → Relay**.  |
| Hub offline          | Clients connect to the room, then close and report a connection failure. |
| Hub restart          | Clients close and re-handshake with their stored device key.             |
| Wrong token          | The Worker rejects the upgrade with `401`.                               |
| Revoked device       | The hub rejects the device and the client stops reconnecting.            |
| Version mismatch     | Update the web client and hub together.                                  |

## Security notes

- The relay sees ciphertext, frame sizes, timing, room ids, and connection
  metadata. It does not see prompts or replies.
- The client token is shared by devices. It is not the encryption key.
- The hub panel is loopback-only. Use an SSH tunnel if you need to reach it
  remotely; do not expose it to the internet.
- Enter the Cloudflare API token only in the hub panel over loopback or HTTPS.
  The hub uses it for the deployment and never returns it to the browser. Saving
  it is optional and encrypted with the hub secret key.
- Use HTTPS for the web app. An HTTPS page cannot open a `ws://` socket.
